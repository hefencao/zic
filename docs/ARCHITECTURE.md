# zic Architecture
本文件描述当前生产代码的稳定所有权、依赖方向、数据流和生命周期。
## 1. 架构目标
- **Historical exact-carrier trust is read-routing policy, not identity proof.** 当当前 `DownloadId` 的 exact/verified cache miss，但 persistent backend 存在相同 `ContentId + sourceRevision` 的完整 READY 历史 exact carrier 时，`ArtifactCacheManager` 才可按用户策略决定是否把它作为只读 body authority：`strictReload` 直接回 source；`reuseThenRefresh` 先用历史 READY，真实 presentation 首帧后再由 `CompositionDownloadTransferRuntime` 通过既有 fresh-source recovery 异步 revalidate current exact；`trustCached` 只用历史 READY，不自动刷新。历史候选不得注册 `VersionPageAuthority`/equivalence、不得建立 canonical `PhysicalMediaId`、不得写成 current exact cache。若同一 logical page/revision 的 READY 候选出现多个 `(length, checksumAlgorithm, checksum)` signature，默认 fail closed；App 可按 external **pluginId** 显式允许“完整文件也信任”，Downloads 只接收 `sourceId -> bool` capability resolver，不认识 Mihon/Venera/plugin。该 override 只放宽候选资格，仍要求 persistent READY 的完整 seal metadata；候选按 persistent logical query 的 `touched_us DESC` 稳定顺序选择。插件 override 只有在全局策略允许 historical reuse 时才生效，不能覆盖 `strictReload`。Reader 只上报 first-visible-frame，不拥有 URI/cache/source 信任策略。
- Reader/media presentation remains source-neutral during stale-carrier recovery. `PipelinePageStream` may project a terminal typed `Failure`, and `LocalImagePlayer` may forward that opaque error through its existing presentation-recovery seam, but Venera/source-generation interpretation stays in App composition. App may refresh the chapter/page authority only for a terminal semantic source failure with no source-owned replacement plan; automatic refresh is limited to the currently visible raw page and once per logical page in that Reader route. The old Reader remains mounted while the fresh chapter is prepared. Replacement occurs only when the failed page can be matched safely and its request/presentation authority actually changes; an explicit page id disappearing is fail-closed rather than index-substituted. A no-change refresh returns to the existing exact-page recovery path instead of claiming success or creating another retry owner. The post-first-frame metadata/version task may obtain a fresh source chapter snapshot for version/reuse analysis, but it is observation-only for `pages[]`: it must not persist or replace Reader transport carriers. Whole-chapter carrier mutation remains owned by explicit source refresh / legacy-locator migration. Stale-carrier recovery may consume a whole fresh source snapshot when the source API requires it, but persists only the matched failed page back into the previous chapter; unrelated exact locators remain unchanged, and sourceRevision/identity drift is fail-closed. A `PipelineReaderSessionHost` chapter is immutable across every input consumed by the session, including page URI, dimensions, byte length, content-kind/animation hints and checksum facts. Rebuilding the host is necessary but not sufficient for reuse safety: the two-minute retention pool may use its coarse key only to locate a candidate, then MUST compare the full `ChapterManifest` session input before resuming it. A candidate with changed page carrier or metadata is disposed and a fresh session is created; identical manifests retain the existing reentry acceleration. Venera `venera-resource:` 是 exact provider request carrier，不是 physical-media proof：同一 `comicId/epId/pageId/sourceRevision` 在真实 jm 设备样本中可随 carrier 返回不同 encoded CRC，且 720×3572 RGBA PNG 解码后像素 SHA-256 也不同，因此不得从 logical page/revision 预先生成 canonical `PhysicalMediaId`，也不得因 URI churn 零网络别名到历史 READY。`DownloadId` 必须继续包含当前 hydrated manifest 的 exact URI；只有已有 version-family projection 或 strong locator/content proof 才能共享 physical owner。Home 的完整 source `upsertChapter()` 即使 revision/pageCount 未变也必须替换 hydrated authority 的 fresh provider locator，同时保留更新的 Reader progress；compact snapshot/progress projection 仍不得覆盖完整 manifest。 Details composition 可以用同 source/comic 下按 chapterId 或唯一 sourceRevision 找到的历史完整 page list 作为页数 presentation candidate，但 candidate 不等于 hydrated command authority：只有 sourceRevision 相同、已知正数 pageCount 与 pages.length 一致且不是 Home placeholder 的 entry 才可直接进入 Reader/单章下载/读状态等正文命令；否则命令必须经 source chapter hydrate。`zic-home-snapshot-page:*` 这类 compact placeholder 只属于 Home/bootstrap projection：不得成为 VersionPageAuthority/canonical media authority，也不得进入 Reader/download `ChapterManifest`、`DownloadId` 或 source resolver；任何正文消费前必须先 hydrate durable full chapter，若仍是 placeholder 则由 source authority refresh，仍无法取得真实 locator 时在媒体 demand 建立前 fail closed。schema-19 只退休短暂错误版本写入的 `volatile-page:v1` physical binding，保留 exact READY、artifact object 与 replica。 - Sealed partial→READY 的跨 filesystem/SQLite 边界由 schema-17 `artifact_promotion` 记录事务进度，但最终 sealed authority 仍只有 `artifact_object + artifact_replica`。journal begin 必须发生在 sealed partial DB proof 已落地之后、正文 rename 之前；store open 只枚举 journal 行并按记录的length/CRC验证 source/destination，绝不读 final sidecar。最终 metadata commit 在单个 SQLite transaction 内发布 object/replica/exact READY/canonical physical binding、退休 physical partial 并删除 journal；journal pending 时 source/destination 都只是受保护候选。same-process duplicate store owner 的 marker guard 必须先于 journal recovery，避免一个本应拒绝的第二 opener 推进第一 owner 的 promotion。 同一 `PhysicalMediaId` 不得长期同时发布 READY `physical_media_artifact` 与 `physical_partial`：一旦 READY replica 已通过正常 preflight 成为可读 authority，旧 partial 只剩冗余恢复状态。bind/READY-open 路径必须触发 persistent-store-owned retirement；`openPhysicalPartialDownload()` 这类 partial 读取/恢复入口若发现 READY 已占优，只能返回 no-partial 并把 retirement 调度给同一 persistent owner，禁止在 read path 内直接删 body/row。store open 还要异步只比较两张 SQLite 表的 key 交集以收敛历史重叠，禁止扫文件树、禁止阻塞 open。retirement 必须在既有 physical-artifact→physical-partial 串行域内重新确认 READY generation，hot borrowed partial 必须跳过；正文/sidecar 删除并确认 absent 后才能移除 partial row，失败则保留 row 作为下一次 retry authority。该清理使用 `StorageWriteScheduler`，不得由 Reader route/App exit 触发或拥有。
- Static/fallback presentation 的实际容器类别由当前 physical generation 的 Pipeline metadata prefix/classification 拥有，manifest/URI 的 WebP/GIF hint 只能参与未决分类，不能在已有 authoritative fallback 之后继续否决 static presentation capability。若 durable artifact backend 已提供 generation-checked `openEncodedPresentationFile()` lease 与 intrinsic dimensions，静态 presentation 应直接把该 encoded file capability 交给 engine，避免先把整包 encoded body 物化进 Dart；真实 WebP 仍由 Pipeline native output/streaming path 拥有。positive static evidence MAY 在稳定 3/7 encoded window 内建立 `targetWatermark=1` 的 one-frame Decode/Upload intent，但 intent 数量不是执行并发：`StagedDecodeRefillPolicy` 只释放当前最高优先级的未满足 one-frame work；fallback/GIF 由 Reader-local ingress 权威分类后终结 native decode branch，并通过 `PipelinePageOutputStream.externalPresentationRequested` 投影 exact external-presentation permission。`LocalImagePlayer` 不得因 mounted、`transferActive`、文件存在或 manifest hint 自行 `_load()`；只有收到该 exact request 后才启动 Flutter decode/presentation，实际首帧回报才满足该 watermark；通用LiveCoordinator的speculative external grant缺省仍为1，Reader profile显式允许最多3个offscreen external-static first-frame并行pending，新的visible/current/transition不计入该speculative cap且可抢占后台等待。不得恢复 96MiB estimated static-output eligibility、固定 current/+2/-1 static gate 或 presentation-owned priority gate。纵向 Reader 的 measured dimensions 改变真实页面 extent 后，即使没有滚动事件也必须在新 layout 后重发同一观察链的真实 `visibleCoverages`；`UploadDemand.viewportVisible` 是由该 observation 派生的 typed presentation fact，不能从 current/next/previous role 猜测。external first-frame 的有界并行只约束 speculative background：Reader当前最多3个offscreen grant，多个真实 viewport-visible fallback仍可越过该cap并行取得presentation grant；若尚未首帧的 visible grant 在期间离开 viewport，LiveCoordinator 必须撤销该 pending grant 并重新释放 speculative refill，禁止 stale grant 继续制造黑屏。这只修正 geometry observation→Pipeline staging，不给 Reader/UI 增加 decode/network/retry owner。native decoded/upload residency 由 `FrameBudgeter` 拥有；FileImage/ResizeImage/MemoryImage fallback raster 由 App composition 显式配置的 Flutter `ImageCache`（100MiB/1000 entries LRU）拥有；encoded speculative I/O 继续由共享 `SpeculativeEncodedReadBudget` 拥有。
- Reader transfer progress 是只读 projection，不拥有下载。`DownloadSession` 将 durable `committedLength/totalLength` 与当前 attempt 的 `networkCursorLength/networkAttemptTotalLength` 分开；后者只在 response lifetime 内存在，`DownloadJob` 在 response open 后立即发布 response total，full-body prefix catch-up 未完成前也不得借此提升 durable resume/seal authority。显示只使用一条共享横向尺度：transport wave 覆盖 `0..networkCursorLength`；当 transport 仍落后于 authoritative partial 时，只在 `transport..committedLength` 画剩余 partial 直线，追平后 partial 不再单独可见。显示总长优先使用已恢复的 durable `totalLength`；若旧 WebP partial 未保存 total，则可从本地 generation prefix 的 RIFF header (`uint32le@4 + 8`) 立即得到 projection-only `localEncodedTotalLengthHint`；active response total 可作为本 attempt 的临时显示尺度。两种 hint 都不得写回 resume/seal/promotion/cache authority；真正无法本地得出总长时不得用固定短条、虚线或任意宽度伪造比例。
- Reader/Pipeline 控制词表不得靠跨包裸字符串或重复阈值维持一致：decode refill 只产生共享 `DecodeWaterlineStage`，该 stage 只描述 DecodeSession refill，不得反馈成 encoded/network admission、另一页面的 body-flow credit 或 memory-pressure network gate。Animated WebP 的 physical-task frame credit 只随**同一页面自己的 role**变化：current/可见 transition unlimited，next/next2/previous 为 5/3/2，稳定 3/7 envelope 内更远页为 1；较近页下载慢、holder depth 不足或 decode waterline 卡住都不得阻塞更远页已有 DownloadDemand 的 transfer。跨页 encoded 压力只由 `NetLane`、source bucket 与共享 actual-read budget 裁决。0.15 transition/overlap 与 0.5 dominant coverage 使用共享常量，Reader latest-wins gate 的 transition 边界直接读取当前 `RoleResolver.transitionThreshold`。URI 后缀只作为容器 evidence，由 Pipeline 统一暴露 WebP/known-non-WebP 判定，`.jpe/.heic` 等已知静态后缀不得在 runtime 被重新当成 unresolved WebP 去预建 native output。用户 pause/speed 的跨 generation 默认只由 `UploadRegistry` 保留，具体 `UploadSession` 只保存自身 user-pause + viewport-freeze 合成状态；`PipelineReaderSession` 不得持第三份 pause 镜像。`HomeLibrarySession.dispose()` 只停止 Flutter 通知，不能代替 owned resource teardown；`close()` 必须 single-flight 并在 dispose 之后仍能真正关闭 library/chapter/whole-comic owners。Home 的 download-composition capability 也只在 `HomeLibrarySession.resolveDownloadComposition` 正规化一次：显式 composition 优先，否则才消费 chapter service 自带 provider；bootstrap、handoff 与 cache binding 只复用该结果规则，不能各自复制 provider cast。 长生命周期 Settings route 同样不得捕获 `WholeComicDownloadQueue`、`ResourceCacheCoordinator`、storage root 或 chapter-download relay 的 generation-bound 对象；policy/data settings 只能持 generation-following capability binding。cache usage inspect 可以等待已经发布的 adoption，但不得仅因查看设置而强制创建 durable core；clear/trim 属于显式 durable mutation，必须先确保并采用 current core generation，并在一次操作内固定同一 coordinator。 chapter-download relay 的 capability identity 变化也必须通过 handoff change signal 发布，使已打开的 Data Settings 立即更新可用性。 Whole-comic policy 设置同样不得捕获某一代 `WholeComicDownloadQueue`：读取只经 `HomeLibrarySession.downloadProjectionChanges + wholeComicQueueSnapshot`，写入只经 `HomeDownloadCommands.updateWholeComicPolicy`，因此设置 route 在 durable handoff/service replacement 后继续跟随当前 generation。用户显式 library backup 也不得由 Settings/UI 逐 section 拼装可穿插的 store 读取：当前 generation 的 library owner 通过 `ImportedLibraryBackupSnapshotStore` 提供一次 semantic snapshot；SQLite 在先 flush Reader checkpoint 后，以一个无 await 穿插的 read transaction 同时读取 chapter/progress、SavedComic、分类、偏好、已读、source preference 与 migration issue，Memory/Lazy 保持同一语义；Lazy 的显式 backup 属于 library durability action，必须先 single-flight materialize/merge durable library，避免已有磁盘数据在 bootstrap handoff 窗口被 memory projection 遮蔽。长生命周期 `LibraryDiagnosticsScreen` 同样不得冻结 route-open 时的 `ImportedLibraryStore`：Home 只注入动态 current-store resolver，并监听 `HomeLibrarySession.libraryGenerationChanges` 这一窄 generation signal；refresh/copy/ack 在完成前必须重验 store generation/identity；切代中的旧 read 必须转到当前 library，ack 只能用 schema/entity/legacy key/resolved source/details/createdAt 组成的 semantic issue identity 在新 store 重新定位其 local `issueId`，绝不能跨 store 重放数值 `issueId`；普通 Home projection/download publication 不得触发 migration diagnostics 重读。持续打开的 Local/Remote Comic Details 也不得订阅 route-open `ChapterDownloadService.changes` 作为 Home live authority：Home 只注入 `HomeLibrarySession.downloadProjectionChanges` 这一 generation-neutral projection signal，signal 到达后由既有 `HomeDownloadCommands` bulk-inspect 当前 generation；跨 signal 的 in-flight inspect 结果必须按 projection revision 丢弃，且 current-generation `idle` 有权清除旧 generation 的 active 状态。standalone/widget 构造可保留 direct stream fallback。
- Reader route 进入 `inactive/hidden/paused/detached` 后，用户播放状态不变，但 Pipeline playback MUST 临时视为 paused；`resumed` 后按用户原 `paused/speed` 恢复。后台不得继续 Animated WebP decode/upload/present，也不得用 worker 重建、CPU affinity 或 raster 降质掩盖生命周期问题。
- 前台 current Animated WebP 的 decode raster MAY 由 `PipelineReaderSession` 内部的 measured-throughput governor 临时降档，但唯一输入必须是该动画实际 `nativeDecodeMicros` 与自身 frame cadence，不得读取 power-save/cpuset/CPU affinity 作为策略事实。full raster 连续超预算后允许降到2/3，若 lower raster 仍连续超预算可继续单向降到1/2；降档在同一 Reader session 的 animated/未决相邻页间保留，避免每页重复支付 full-raster 慢帧。恢复 full 必须先在降档态连续证明明显快于 cadence，再只于后续 page boundary 执行；当前页确认 static 可直接恢复。Reader route detach/re-attach 重置该瞬时性能状态。该策略只改变 DecodeTarget/presentation pixel carrier，不得改变 source geometry、3/7 download window、decode waterline、网络/缓存 authority 或用户 playback state。
- Reader route 覆盖 Home 期间，`HomeLibrarySession`仍可更新并持久化 progress、version relation 等非 carrier authority，但隐藏 Home MUST NOT 因后台 publication 整树 rebuild；首帧后的 metadata/version source snapshot 本身不得持久化 `pages[]` carrier，route 返回后只统一刷新实际发生过的 Home publication。 App 根部的 theme shell 只观察 `AppPreferencesController.themeChanges`（当前仅 `themeMode/amoledDarkTheme`）；总 preference `ChangeNotifier` 继续服务设置页、Home 的字段级过滤与持久化，但 comic Reader/adaptive-profile 写入不得失效 `MaterialApp` 或被 Reader 覆盖的 Home route。Reader 首个实际 presentation frame 后的 metadata/version refresh 必须真正异步调度，不能在 first-frame callback 栈中同步执行到第一个 await，也不得成为 current page source-plan 的前置门槛。 播放专属控件的可见性只能来自真实媒体能力证据：manifest/后缀/`animatedHint` 只允许作为预取或分类提示，不能让 pause/speed 先验显示。unknown 默认隐藏；codec/decoder 观察到至少两个实际帧即可立即确认 animated，完整静态证据才确认 static。 Venera source semantic retry 的“单次恢复链”与“用户显式新一轮下载”属于不同 generation：同一 generation 内 `onLoadFailed` replacement 仍有有界上限（当前 5），普通 provider/network retry 不得重置；当 semantic media rejection 后 source-owned `retryResource/onLoadFailed` 已无 replacement plan 时，`SourceResourceTransport` MAY 在同一 NetLane task、同一 `TaskControl`、同一 logical open 内对相同 opaque locator 做且仅做一次 fresh request-plan `resolveResource` re-resolution；该步骤不得重置 replacement budget、不得创建 Reader/UI retry owner，若 re-resolved plan 仍 semantic reject 才升级为 `recoveryUnavailable` 供 App stale-carrier refresh；仅当章节命令最终以 `ErrorCode.source` 失败且用户显式 retry 时，才可针对实际失败的 source-owned locator 开启 fresh resource generation。若旧任务跨进程/版本恢复后只剩 failed chapter state、内存 locator 集已消失，则同一次显式 Retry 可先按旧 generation 运行到第一个重新确认的 source-terminal locator，立即只 fresh 该 locator，并允许该用户命令继续一次；不得刷新未触达页，也不得让同一 locator 在一次 Retry 内反复 fresh。fresh generation 必须同时失效 host request-plan 与 Venera retained config/resolution，再重新执行初始 `onImageLoad`。 Download Manager 自动缓存消费 durable management projection，而非把 exact `CacheRec` 当唯一存在性 authority。compact Home projection 只提供 chapter identity/pageCount，management cache/snapshot 不得把 `zic-home-snapshot-page:*` placeholder 展开成 `DownloadId`；exact READY/partial 必须按 durable chapter inventory 聚合，canonical 行仍只由 canonical physical inventory/projection proof 建立，禁止为了展示缓存猜 page index。已知 library chapter 的 canonical `physical_media_artifact` / physical partial 必须按 canonical projection 直接计入完成页、字节和 partial 进度，即使当前版本没有 exact READY row；exact binding 只决定 exact/pinned/manual 属性。Reader/后台 durable mutation 只发布轻量 management invalidation；UI 防抖 single-flight 重读。显式 chapter run 期间 invalidation 只记 dirty，最后一个 run 结束后合并补发一次，禁止逐页全库重扫，也禁止吞掉并发 Reader cache 变化。 管理投影表示 durable physical inventory，不等同于 runtime reuse 授权：已物化 canonical physical object 即使当前 relation proof 后来撤销仍可显示为缓存事实，但新的 exact runtime claim 仍必须通过 active `CanonicalMediaChapterAuthority`；同一页同时存在 canonical/stable 物理事实时管理投影优先 canonical 实体。同一 `PhysicalMediaId` 暂时同时存在 READY 与 stale partial 时，所有只读管理/usage projection 必须立即以 READY 为唯一可见 inventory：partial 不再贡献 page state、bytes、entry count 或 trim pressure；投影本身不得因此执行删除。显式 clear 仍可由 persistent maintenance 顺带删除该冗余正文，但不能把它计成第二个 cache eviction。全局 clear/trim 删除 canonical physical binding 前由 SQLite 在同一 `BEGIN IMMEDIATE` 事务内复核 physical LRU generation 与 surviving exact READY 引用，避免 busy/pinned/new exact race 拆掉 canonical routing。
- Android SurfaceProducer 的 `scheduleFrame()` 合并由 texture bridge 按 producer 持续到下一次 vsync；同一 producer 的重复请求共享一次真实平台调度，不同 producer 保持独立首帧调度。
- current 具有最高资源优先级，但目标页首帧不得依赖 current 的下载完成或 holder 深度。
- Reader native media/process prewarm 只能是 acceleration hint：可以在章节 materialization 同时启动，但章节准备/route readiness MUST NOT await prewarm；真实 decode worker/texture capability 在需要时自行 join/retry，并保留错误 authority。首帧/首个 output 是否已呈现不得改写 NetLane local/remote bucket、artifact/cache authority 或 composition-wide local-read pressure。
- Venera 的单 JavaScript invocation context 是 external-runtime 的串行执行资源，不是第二套 Reader scheduler。带同一 `TaskControl` 的 page request-plan 在进入该唯一 context 时继续服从 NetLane 实时 priority：当 priority 达到 controlled pressure floor（当前 780）而 active invocation 是无 `TaskControl` 的普通后台调用时，runtime gate 可以请求取消该 generic invocation；若 active 本身受控则仍遵守既有 rank 差/preemption 规则。取消只请求下层尽快退出，唯一 permit 必须等旧 invocation 的 physical Future/`finished(requestId)` 真正结束后才能转交，不得为抢占增加第二 context。 `Network.*` async bridge waiter 必须记录所属 `requestId`；`__zicCancel(requestId)` 除取消resolver I/O与delay waiter外，还必须同步移除并reject该request的JS bridge waiter，使正在`await Network.*`的source hook立即unwind。迟到native bridge回包在waiter已移除后只能丢弃；这项unwind不得提前释放唯一invocation permit，permit边界仍是`finished(requestId)`。Reader 首帧后的 metadata/version refresh 属于可被这种 foreground pressure 让行的后台调用。`sourcePlanGateBlockedBy*` 只记录 waiter 首次入队时看到的 blocker，用于归因，不代表整个 gate-wait 区间始终由该 operation 占用。 Source metadata 瞬时 JSON parse 恢复也属于该 external-runtime 边界：只读 Venera source invocation 仅在本次实际发生 bridge network call 后抛 `SyntaxError` 时可用同一 `TaskControl` 做一次 `freshNetwork` replay；fresh 必须 bypass runtime HTTP cache，第二次失败即终止。`Cache-Control: no-store` 响应还必须撤销同 URL 的 memory/persistent runtime cache entry；Reader/UI 不得增加 retry owner。
- 同一稳定 identity 只有一个权威 request、session、artifact、cursor 和活动 writer。ContentId/DownloadId/DecodeId 的新 `key` 使用长度 framing，不能把带分隔符的来源字段折叠成同一字符串；旧 cache metadata/SQLite key 只作为兼容恢复输入，新的写入使用 framed key。
- Download demand是consumer claim，不是物理transfer ownership：应用级`PersistentDownloadComposition`持有唯一`CompositionDownloadTransferRuntime`，其`DownloadTransferOwner`按exact `DownloadId`唯一拥有registry/writer/network/retry/hot partial；生产 App 的 network capacity 只由 application-level `DownloadResourceCoordinator.networkLane` ## 3. 包所有权
### `domain`

领域 identity、值对象和不可变实体。`TaskControl` 是 scheduler-owned work 跨层只读控制合同，只暴露 cancellation 与 priority；需要保持已admit工作实时rank的下层可选择观察scheduler-owned priority change，但只能重新评估既有执行资格，不能写priority或形成第二调度器；消费层不得借此拥有调度策略。不得依赖 UI、插件、网络、缓存、数据库或平台桥。

### `catalog`

漫画源、漫画/章节/page manifest、来源能力和 catalog cache identity。`CachedBrowsableComicSource` 缓存 browse、details、preview/comment 分页和 chapter metadata，所有这些可重新获取的响应共用注入的 `ResourceCacheManager`，但按稳定 response identity 分开；它不拥有 artwork 加载，Reader 页面正文仍透传到统一 Pipeline。

### `resource_cache`

封面、详情、搜索、章节元数据等可重新获取响应的唯一缓存平面，拥有容量、TTL、分类预算、in-flight 合并、持久 byte store 和失效策略。Android `local-folder` 导入保持正文 SAF/document-tree identity，不复制整本图册；但 cover 是独立的长期 artwork resource：根目录签名有效且主名精确为 `cover` 的图片优先作为封面并从 Reader 页序列排除，否则第一页同时承担封面与正文。App composition 在显式导入/刷新时预先 materialize retained cover：静态格式可由 `local_media_bridge` 生成约512×768的有界 derivative；GIF/WebP animation candidate 则持久化原始 encoded cover，避免把动画所有权错误降格为 Bitmap 首帧；同时可以在独立 `cover-placeholder` retained key 上保存小型静态 derivative，Home 仅把它作为 presentation acceleration：placeholder 命中时先真正画出一帧，再切到独立加载的原始动画；placeholder miss/失败只后台 lazy materialize，不能成为最终 cover 的等待条件或第二 artwork authority。`ImportedChapterRecord`/compact Home projection保存 cover media format 与 animation hint，旧完整记录可由 matching page 补回。Home/Bookshelf 只消费对应 canonical retained artwork，旧导入记录允许在首次 cache miss 时 lazy materialize。

### `transport`

可取消、可分块的 encoded-byte transport、range、validator 和 response 合同。Reader page 使用可选 `ControlledTransport` 将 scheduler `TaskControl` 贯穿 cache read-through、source-plan、open与response body；任何transparent/read-through wrapper若下层支持controlled capability都必须保持同一control，不能因cache miss降级为普通`open()`。transport可中止自身请求但不拥有priority policy，也不得在请求真实退出前伪释放lane容量；prefix probe后outer stream取消仍必须abort底层response。它不拥有artifact、Reader demand或播放状态。 `SelfBoundedOpenTransport`只允许lower transport在指定URI的完整open生命周期已经由自身有限deadline覆盖时声明；此时DownloadJob可省略generic 6s open watchdog，但仍保持同一TaskControl cancellation与6s body-read inactivity watchdog。external source只有runtime source明确暴露resource-operation deadline且最终direct media transport也自有open deadline时才可形成该proof；当前production Mihon/Venera runtime分别由executor的45s/55s invocation limit约束，`RhttpSourceResourceDirectTransport`另以15s约束client/header open并在header timeout时取消native request。显式chapter download的LoaderTransport可直接携带该proof；Reader的`ArtifactCacheTransport`不得把整个wrapper伪装成self-bounded，因为origin前仍有本地cache lookup/foreground阶段。Reader现在保持外层generic 6s watchdog覆盖这些本地阶段，只有在本地阶段结束且即将进入已证明self-bounded的origin fallback时，才通过scheduler-owned `OpenPhaseReportingTaskControl`报告一次phase handoff，由同一DownloadJob撤掉当前open timer并继续等待同一pending future/CancelToken；lower层不能设置timeout值、retry、priority或admission，body read仍由原6s inactivity watchdog负责。 `ComicSourceResourceGateway` 的 per-page self-bounded proof 必须与 controlled response loader 作为一个 composition capability 原子传递到 `LoaderTransportSource.selfBoundedOpen`；App/LocalMedia 只传函数而丢失该 bit 会让 `ArtifactCacheTransport` 无法报告 phase handoff，从而错误地让 generic 6s timer覆盖 Venera/Mihon 已由 runtime/direct owner 自限时的 source-open 阶段。generic open watchdog真正超时时，DownloadJob必须只abort当前controlled open attempt的私有control，而不得cancel真实scheduler `CancelToken`；该attempt control持续透明代理实时priority/priorityChanges与scheduler cancellation，因此owner仍看到`ErrorCode.network`并可按既有retry继续。已超时的cache/storage lookup即使稍后物理完成，也必须在attempt-control取消检查处终止，禁止在NetLane task已归还后再跨入origin fallback；真正scheduler cancellation仍沿原CancelToken下沉。

### `storage`

partial artifact、连续前缀、校验、seal、原子 promotion、索引和临时 workspace。对稳定 DownloadId，已经提交并成为 playback authority 的 partial prefix 单调不减；网络 attempt 重启、validator 缺失或 Range 被拒绝都不能删除、缩短或重建该 prefix。partial append只写入并推进长度，不在UI isolate逐chunk计算CRC；seal/restore在isolate rehash后提交权威checksum。partial→final promotion的filesystem rename与内存state切换属于Artifact内部事务，所有encoded read必须由Artifact按preferred/alternate path直接open同一authoritative file handle，Reader/sessions不得观察或猜测rename窗口。它不决定页面角色或网络优先级。 Android SAF 的 provider document-id/children-listing 缓存只属于路径解析加速，不是文件存在性authority：正常 create/delete/rename/replace MUST仅失效实际发生mutation的父目录listing；stale exact locator第一次恢复也只失效目标父目录。只有父document-id无法解析，或scoped recovery后仍失败并怀疑祖先目录被外部整体替换时，MAY退回整tree cache invalidation。

### `downloads`

composition-owned `ArtifactCacheManager`、artifact transport/read scheduler、verified-equivalence proof、章节/整本持久下载与来源 transport 组合。页面 session 状态本身由 `sessions` 拥有。

### `media`

encoded source、cursor、frame、output、renderer 和只读 timing capability。它不选择页面角色或 scheduler 策略。

### `sessions`

`DownloadSession`、`DecodeSession`、`UploadSession`、registry、claim/lease、frame holder、playback timer、Net/Decode/Upload lane 和 `LiveCoordinator`。它是可变媒体状态的权威所有者。Presentation 已证明某一 artifact-backed generation 无法语义展示时，`DownloadTransferOwner` 还拥有该 physical id 的恢复事务：recovery barrier 先冻结新 admission 并 quiesce local preparation/NetLane task，再由 composition cache owner 失效对应 durable authority；若该坏 generation 已经形成 promoted ephemeral final，recovery reset 必须显式销毁该 final 后再 restore，禁止普通 `DownloadSession.reset()` 默认保留 final 的语义把同一坏正文重新恢复成 promoted。普通 reset 仍默认保留 promoted final，只有 presentation semantic rejection 这类已有正文无效证据的路径可以请求 destructive final reset。成功进入recovery后，`ArtifactCacheManager` 对被恢复的 logical id 与其当前 resolved physical id 建立 transient fresh-source quarantine：`PartialDownloadHandoff`在选取canonical physical READY/partial之前也必须检查该状态，memory、persistent、backend-internal equivalent 与 direct-equivalent fallback同样视为 miss。quarantine 初始unarmed，只有physical session reset以及旧canonical physical READY/partial routing失效完成后才由composition arm。普通unpinned cache仍由fresh durable store解除；若rejected exact是显式pinned/manual binding，cache backend只暴露窄retention fact，composition保留该exact durable对象、让fresh epoch保持hot-only，并在automatic handoff处解除quarantine而不重新绑定canonical physical或覆盖exact。若已有required chapter/whole-comic claim，它仍留在同一个physical session上并继续作为exact durable completion owner，不受hot-only automatic策略限制。随后才以原claims重启；task retirement不得越过此barrier抢跑。Reader ingress registry必须同时保持physical object generation与Reader encoded generation边界：unfinished/failed或pending-late-attach source按DownloadSession object identity换代；already sealed/sourceReady/no-failure且无pending attachment的same-exact immutable projection可跨transient physical session recreation保留。旧same-id session teardown必须校验concrete session identity，不能删除replacement entry。synchronized late join只有Reader-local projection自身追平稳定physical epoch/length/sealed且无failure后才能加入live fan-out；replay期间consumer通知可暂时隐藏，但publish必须以replay开始前的projection snapshot作为事务基线与最终状态比较，不能在prefix/kind/revision已更新后才截取`before`。Reader source watch把encoded content classification与native source growth同等视为decode evidence：`unknown→fallback/gif/webp`必须立即wake waiting decode，尤其fallback/gif不得被`sourceReady=false`或尚未seal的partial prefix阻塞到下一次手势/reconcile。deferred resident range hydration对同一physical `SourceEpoch`的失败是Reader-local终态：失败后不得仅因requested length尚未满足就在microtask tail中自递归重放，也不得由role/priority churn重新消费同一失败authority；只有新的physical epoch可以重新尝试。成功中的hydration若同时收到更大的decoder-owned target，仍可在当前成功attempt结束后只接续一次最新target。UploadSession dispose是generation retirement barrier：旧generation即使仍有pending prepare也必须立即退休其uploader slot，old async ### `pipeline`

把 `ReaderObs` 纯计算为角色窗口和 `DemandPlan`。它定义优先级、水位和 keep 集合，但不创建 transport、artifact、cursor 或 texture。

### `pipeline_runtime`

Reader 章节资源会话的唯一组合所有者。它把 demand reconcile 到 download/decode/upload session，发布 `PipelinePageStream`，管理 frame budget、共享 page download lane、artifact handoff 和短期资源会话 retention。短期 Reader re-entry retention 的 idle LRU 最多保留最近两个 exact session key、TTL 仍为两分钟；第三个 key 立即淘汰最旧项，且只有已释放 decode/upload/ingress/streaming source 的 media-empty shell 才有资格进入。短期 Reader re-entry retention 只允许保留 download/physical transfer/encoded source authority；route 退出进入 retention 时必须立即释放全部 Reader-local decode/upload session、native cursor/WebP canvas、decoded frame 与 output/texture ownership，禁止为了两分钟快速重进让 cursor 的 source `Arc` 继续钉住已可由 transfer/artifact 重放的整页 encoded bytes。它也接收 Presentation 的语义失败反馈并保存最后一次 page-body authority：artifact-cache body 的展示失败可触发每页每 Reader session 一次自动恢复；显式重试走同一 composition recovery。cache 等价复用时必须保存实际 `storageId + mutation generation`；恢复只能条件失效产生失败字节的那一代，旧 failure 若晚于 authority 换代到达只能重载当前 generation，禁止删除或 reset 新 authority；真实失效成功后本 logical/physical recovery group 必须临时禁用全部cache/equivalent source reuse并销毁已被否定的ephemeral promoted final；quarantine 只有在 destructive reset 完成后才 armed，且只有 store 开始时已 armed 的 fresh exact durable handoff 可解除，reset 前启动的旧 handoff 不得解除；禁止从session final或sibling binding回灌同一坏正文；`fallback` classification 本身不授权删除。

### `pipeline_native`

把 native source factory、cursor、frame uploader、output projector 和 prewarmer 作为原子 capability 注入 `pipeline_runtime`。核心 Pipeline 不直接创建具体 FFI 或 Android texture 实现。

### `reader_runtime` / `reader`

`reader` 提供 observation、导航和通用 Flutter Reader；`reader_runtime` 负责产品交互、尺寸投影和 `ReaderObs` 适配。二者都不拥有资源 session、缓存或 native handle。页面错误 UI 可以报告 presentation failure 和发出显式“重试”命令，但恢复资格、cache invalidation、session reset 与 network re-admission 全部留在 Pipeline/composition owner。

### Home 冷启动组合

`apps/app` 的 Home 关键路径只等待能产生封面的本地库 primary 数据和内置来源。入口直接挂载 memory-backed Home；首个Flutter surface可见后异步打开durable/native/plugin capability。`HomeProjectionSnapshot`同时保存Home primary、SQLite projection revision和需要持久展示的manual/auto-cache chapter-download summary。revision匹配的durable handoff只切换authority并targeted revalidate这些已持久download identities，禁止为了Home启动扫描全部library entries或执行orphan discovery；后者属于Download Manager/用户显式刷新。无可信snapshot时才允许一次full recovery reconcile。targeted/full reconcile更新后先比较真正持久化的download summary/orphan projection，无变化不得重写snapshot；这移除了此前设备上56-entry同步projection约895ms+3.26MB snapshot encode/gzip约289ms的无效启动竞争。队列和章节下载增量仍通过Home独立download projection更新水印，不得重发library broad notify。durable artifact/cache owner 在 exact READY promotion 或 canonical physical partial checkpoint 真正提交且 mutation generation 仍有效后，必须发布独立 management-projection invalidation；Download Manager/Home management projection 只能把该信号当作重新读取 durable inventory 的触发器，不能把旧内存 projection 当 authority，也不能在 stale/rollback 分支误发。外部插件在capability handoff后后台恢复，source尚未ready时外部封面保持pending，source projection single-flight释放owner时必须重检尾部change。 `HomeLibrarySession.close()` 在发布 `_closed` 与关闭 owned SQLite/library 前必须排空已 admission 的 snapshot write tail；`DemoHome.dispose()` 只启动异步 composition close，`ChangeNotifier.dispose()` 必须在该 close 完成后执行，不能抢先取消已接纳快照。

`MainActivity` 显式创建关闭自动 `GeneratedPluginRegistrant` 的 `FlutterEngine`，并在 Activity 结束时销毁；仅覆盖 `configureFlutterEngine` 不能阻止 implicit engine 的构造期注册，feature bridge 只能通过 startup channel 按能力挂载。`LocalMediaBridge` 在 Android 的 pick/scan/open/read 入口前共享 single-flight attach，保证从持久阅读记录直接进入 Reader 时也先注册 `dev.zic/local_media`；startup channel 不存在的宿主才回退其自身的 eager registration。按类名反射的 Android feature plugin 及 rhttp 入口必须由 app 的 R8 keep 规则保留原始全限定名。Android 存储根目录优先随 Dart entrypoint args 同步注入，避免冷启动首次 MethodChannel 往返；旧宿主才回退轻量 startup channel。Android 的 durable/native/plugin capability 只能在 `FlutterActivity.onFlutterUiDisplayed` 已确认首个 Flutter surface 实际显示后打开；Dart `postFrameCallback` 或“已经 rasterized”的调用方假设都不是可见性证据，也不得据此提前放行重 I/O。该阶段不创建第二份 owner。
首次安装的 `app_preferences.json` 不在 Home 启动时强制写入；偏好控制器先使用内存默认值，用户首次修改时才创建持久文件。
`AppPreferencesController` 负责持久化 `ThemeMode` 与 AMOLED 深色开关；`MaterialApp` 只在有效深色主题下应用 AMOLED 纯黑 surface/scaffold/canvas，首帧加载背景不再强制切换为浅色。App 根路由的返回确认由 `_RootBackExitGuard` 拥有：它以 `PopScope(canPop: false)` 包裹 Home 根路由，首次系统返回只显示“再按一次返回到后台”提示并开启 2 秒确认 Timer；窗口内再次返回仅通过 Android startup channel 请求 `moveTaskToBack(true)`，保持当前 Activity、FlutterEngine、Dart services、Reader/transfer owner 原位存活，不等待 checkpoint、service close、偏好 flush 或任何 durable I/O。根返回是导航/后台化动作，不是应用 shutdown barrier；不支持该 Android capability 的宿主才回退 `SystemNavigator.pop()`。真正 service/runtime close 仍按各 owner 自己的 teardown 合同收尾。守卫只挂在根路由上，其他路由、对话框与漫画源页内部返回手势（含其 `WillPopScope`）先于该守卫消费返回事件。

新安装且不存在 imported-library、offline-cache 或 whole-comic queue 状态时，Home 不打开 SQLite 或创建 WAL/schema；`LazyImportedLibraryStore` 先提供内存投影，首次 chapter、收藏、已读、偏好或进度写入时迁移到持久库。已有 durable state 的服务仍在 Home 可见窗口之后打开；Reader checkpoint writer 的第二个 WAL 连接也只在首次真正写入 `ReadingProgress` 后懒启动。SQLite schema 11 在 schema 10 的独立 `chapter_read_state` 基础上新增 `source_migration_journal` 控制表；`chapter_read_state` 继续作为独立的来源章节身份状态，不再用指向 `imported_chapter` 的外键阻止未 hydrate 章节先写入已读状态；显式删除章节负责清理章节、进度和已读状态。

已有 durable state 时，`HomeProjectionSnapshotStore`先读取上一次成功reconcile的Home投影；bootstrap Home只读该快照，SQLite仍是章节、进度、书架、偏好、分类、已读和版本关系唯一事实源。snapshot revision匹配时Home primary直接复用；显式App退出在其它Reader/download/plugin owner静止后、library close之前flush最终Reader progress并强制`checkpointSnapshot()`读取最新revision，保证下次启动不会因退出尾写误触发authoritative reload。compact entries不复制完整page locator；Reader/下载/版本迁移前再由authoritative library hydrate。snapshot损坏/版本不兼容/读失败静默回退SQLite。snapshot序列化仍是加速器而非事实源，真实状态变化异步原子写回；无变化的download校准不得制造重写。

详情头部先投影已持久化的 successor/predecessor 关系，来源版本发现只在后台校准并更新持久关系。正文喜欢、书架、收藏、下载整本保留统一 48×48 `_PreferenceButton` 尺寸与 `filledTonal` 外观，不得因不可见版本槽或整组缩放产生来源间尺寸差异。版本入口位于顶部 AppBar 的“迁移漫画源”图标左侧并直接复用该行 `IconButton` 风格；无关系时只保留标准 action 宽度的空槽，仅有新版、仅有旧版、新旧并存时分别使用正向、倒置、顺时针90度的感叹号。版本面板在新/旧列表间原地翻转，行标题直接查看详情、行尾迁移图标直接进入既有对比；不得显示 opaque comic ID、伪 generation 编号或再弹出版本次级选择菜单。
持久关系首显后的 source refresh 必须二次发布到当前详情和已打开面板，不得要求退出重进。面板中间的“迁移到当前版本”是真实命令：只有当前版本存在不同 canonical identity 的 predecessor 时才可用，并直接进入既有迁移对比。同源替换在移除旧版本记录前，必须将已验证等价且已持久化的旧页面 artifact 写入目标 exact DownloadId；等价关系仍不是 hard alias/rekey，无法证明等价的字节不得复用。

漫画源页使用来源自身声明的 browse section：Mihon 映射 Popular/Latest，标准展示顺序为“最新 → 热门”，Venera 枚举 explore loader 与 category target；首次进入来源时默认 section必须由**当前展示顺序的第一项**决定，不能另写 `popular` 默认值，也不能让最近一次 catalog cache projection反向选择 UI。未来用户自定义排序若改变 Presentation顺序，同一排序 owner自然同时决定默认焦点。原生/Mihon/Venera 仅通过来源 chip 的背景色区分，不显示 JS/插件图标，也不占内容分类行。`FilterableBrowsableComicSource` 只投影来源真实 `FilterList`：空 schema即没有筛选入口，不另设容易漂移的 capability布尔值。Mihon bridge必须按官方 `Filter.Header/Separator/Select/Text/CheckBox/TriState/Group/Sort` 基类继承关系识别插件自定义子类，并保留 Group层次与 Text/Sort状态；用户修改以类型化 filter-state override进入 search request。筛选是否激活是独立 Presentation/request mode：空 override表示使用插件默认 `FilterList` 状态而非“未筛选”，激活后分类栏焦点属于“筛选”且请求不继承 latest/popular section；Catalog cache identity与runtime payload必须显式区分 filter mode和普通 section mode；external browse的 typed factory、wire validator与 adapter payload必须共享同一字段契约，schema v1新增 `useFilters` 可缺省兼容但未知字段仍拒绝。Filter不得伪装为 `SourceBrowseSection`，浮动搜索只拥有 query与搜索历史；搜索展开与输入只更新自身 listenable 子树，IME inset只按“键盘高度减去浮层原始底部净空”的实际重叠量移动搜索浮层，不得压缩或重建 catalog 网格，固定搜索浮层和底部来源栏保持独立 repaint boundary。键盘 inset 开始递减时必须立即释放输入焦点但保留搜索面板，使下一次返回只关闭面板且不得重新请求 IME。browse projection revision 只属于 metadata，不能作为整页 artwork reload token；source card 的 Sliver child owner 使用 canonical comic identity，raw locator变化不得重置封面 State。固定大小的 catalog page 仍使用显式上一页/下一页，pager 位于内容滚动尾部。列表由 catalog response cache先行投影，但 cache只能服务**当前精确 UI 请求**，不得用“最近 projection”改写 section/query/filter默认状态；source切换时 projection owner先原子切换到目标 source，旧 source内容没有展示资格。后台 refresh只有在稳定字段发生变化时才更新 Presentation；边缘下拉达到刷新阈值后强制绕过缓存请求来源，但保留当前内容直到新数据到达。Mihon 插件的已安装与仓库列表仍按规范化语言分类。

详情页与漫画源页的统一刷新由 `AppPullToRefresh` 拥有 edge trigger、72 px位移、进行中状态与成功/失败结果图标；页面不得叠加第二套刷新状态。

详情入口采用 stale-while-revalidate：若 `CachedComicDetailsProjection` 有热 manifest，页面先同步投影漫画和章节，并复用已缓存的首屏预览/评论；主详情请求和可选预览/评论请求在后台刷新。Presentation 按漫画字段、章节列表、预览页和评论页分别比较，只替换发生变化的那一类，失败的可选请求保留旧投影。内嵌在新 manifest 中的首屏页只在强制主响应刷新后同步到对应分页 key，分页独立刷新不会被普通主响应命中覆盖。预览图/头像的编码字节仍归 `ComicSourceResourceGateway/ResourceCacheManager` 的 artwork 路径，不归 catalog metadata cache。
同一详情 route 的 `route-push`、`details-first-frame`、`deferred-source-ready` 因果 trace 必须使用 composition-owned monotonic clock；独立组件测试/嵌入场景可以回退到组件本地时钟，但不得把不同 epoch 的时间戳混在同一跨组件时序结论中。详情首帧不得等待下载状态、artifact index、章节 page I/O、跨版本 page mapping proof，或 deferred external source activation。已有持久化详情投影时必须先 push route 并完成详情首帧，外部 source activation 只能从下一次 post-frame 异步启动；source 后续到达时原地更新同一个 `LocalComicDetailsScreen` identity/State 及其 source-dependent capability，不得重建详情局部状态或要求退出重进。章节状态检查在首帧后以 `inspectMany()` 批量读取；跨版本关系发现由详情/version-state与Reader后台refresh共同消费同一source capability：详情不得遍历整本，但version-state发现relation后可异步warm实际有缓存状态的当前chapter。普通Reader入口只恢复已有mapping并立即进入Pipeline，不得因为mapping缺失或旧proof模型而同步扫描/重验同漫画历史relation；generic mapping补全留给Reader启动后的异步metadata/version refresh。只有显式“查看版本”拥有明确`targetComicId`时，reuse preparation才以短生命周期Future传给目标Reader，并在目标physical demand前只对selected direct relation的当前hydrated chapter执行single-flight bounded最多3-anchor准备；该selected relation已有当前`intervalProbeVersion`时直接跳过。普通Reader的chapter metadata/version relation后台刷新必须等首个实际页面presentation frame报告后才启动，再刷新当前chapter existing-state alias；它不得在首帧source request-plan之前抢占Venera单context runtime gate。late proof只影响尚未acquire的demand，已存在physical session绝不merge。显式version-view的selected-target preparation仍是例外：它属于目标physical acquire前的正确性边界，不得被该首帧后移规则延迟。不挂lazy resolver、不为未来页占alias、不在翻页lookup时调用source。Reader、DownloadSession、NetLane正文与调度ownership不因该后台准备下沉到详情/UI。
详情扩展数据由 source adapter 负责：`ComicManifest` 可携带首批预览缩略图和评论，`ComicPreviewSource`/`ComicCommentSource` 只在来源声明能力时提供继续分页。App 只消费
规范化 URI、评论字段和不透明的 `sourceSubId`/回复 ID；评论正文的受限 HTML 只解析实体、换行和 HTTP(S) `img`，emoji 仍通过统一 artwork loader/cache 绘制，不把原始标签直接交给文本控件。图片仍走统一 artwork cache，评论完整列表和回复通过详情次级页加载，不把评论请求或插件 transport 变成章节目录的
全局门控。Venera 直接复用 `comic.loadThumbnails` 与 `comic.loadComments`，因此已有 `ComicDetails` 能力的来源可渐进显示预览、评论和回复。预览 URI 保留 Venera 的
`@x/y` 裁剪标识用于预览项/widget/painter 的单项身份，但 `onThumbnailLoad` 请求回调接收
去掉裁剪标识的原图地址；该 base URI 也是编码字节缓存身份，App 解码后只绘制对应裁剪区域。
预览栏折叠与展开共用同一套顺序布局。实际行含横图时最多 2 张，纯竖图行最多 3 张；只允许在相邻三个候选内做最小局部重排。完整行直接用全部媒体宽度反算等面积 tile，不再把剩余宽度变成外边距或巨大项间距；标题保留普通内容边距，但图片区不叠加 Card 或水平 border/padding。只有稀疏末行允许相对完整行放大，面积上限为参考完整行的 2.4 倍。阅读设置提供每行最大数量 1–8，默认 4。折叠态只显示同一布局第一行，高度取第一行实际高度；展开态继续消费来源分页，并由 `PageView` 左右分页呈现后续行。展开图片区域按屏幕高度 90% 封顶，开关位于中间且只显示上下箭头。行规划优先使用 `ComicPreviewAsset.width/height`，缺失时以解码后的可见裁剪尺寸回填；缩略图使用 `BoxFit.contain`，不拉伸或强制裁切。预览失败只显示按资源 identity 生成的柔和单色占位，不显示破损图片图标。

App-owned modal panel 的操作行由 `AppDialogActions` 统一投影：关闭固定为左下角 X，确认、
保存或删除位于右侧，不再使用“取消”文字按钮。

- `plugin_host_bridge`：Android 隔离进程与 Mihon/Venera runtime 适配。Mihon 设备发现只覆盖作为系统共享 APK安装的扩展，合并 `getInstalledPackages`、`getInstalledApplications` 与已知仓库 package name的精确 `getPackageInfo`；每个候选的 collision，慢候选不得占住提交队列。manifest 已保存的 payload 元数据可跳过重复 Dart inspection/hash，隔离 runtime 仍必须在加载前校验 payload 长度与 SHA-256；设备 Mihon 扫描可与插件激活并行。漫画源页底部控件只投影已经产生活跃 source session 的插件；已安装但未启用/激活的 Mihon 或 Venera 只保留在管理页，不得作为 disabled 来源控件出现。typed denial/runtime code判定不可恢复时才回滚新记录并删除新 payload，可恢复失败保留记录和 payload并由管理页或仍有旧 session 的控件触发同一 pluginId 重试，replacement 失败继续保留旧 session；从漫画源管理页返回不得等待后台库重载。插件管理页进入时按每个已安装插件的受信仓库来源执行 `ExternalPluginController.checkUpdates`（版本号优先比较，无版本号时版本串不同即可更新；单个仓库不可达不掩盖其它仓库结果），发现更新以对话框提醒一次并在已安装行保留徽标，仓库行对已安装且可更新的条目显示"更新"。已安装 Venera 插件支持直接编辑 JS：`readVeneraJavaScript/saveVeneraJavaScript` 把编辑内容写入新 revision payload、重新经过受限元数据检查并以新摘要固定后走与安装相同的 approveAndActivate 事务替换会话，检查或激活失败时旧 payload 保持权威。来源管理页是单一未分类的可拖动排序列表（`_buildManagementEntries/_managementList`）：Mihon 同扩展多语言变体按 `mihonSourceGroupKey` 折叠为一行，行代表 = 最近启用变体（`ComicSourcePreference.lastEnabledAt`），点击行首插件图标展开其余变体，`_enableMihonVariant` JavascriptInterface 线程。激活只等待源代码显式 `await` 的请求，激活期间遗留的后台请求由下一次 invocation 的 activation-work gate追平；`requestId` 取消与 runtime close 均先取消 resolver transport，且只有 JavaScript `finished(requestId)` - `bridge`：Dart FFI、native source/cursor/frame ABI 和两个进程常驻 decode isolate。
- `texture_bridge`：Android texture lease、SurfaceProducer、单 lane RGBA blit、schedule 和 release；精确尺寸的 idle prewarm 在同一 blit lane 先 materialize surface，并用 acceleration-only native prepare 预配置目标 RGBA geometry。prepare 只减少首个真实 blit 的平台配置成本，不能取得 surface correctness authority：每次真实 blit 仍独立读取/校验 ANativeWindow geometry，并在失配或 lock recovery 时自行配置。满池时只淘汰最旧 idle lease，不能把 surface 初始化或无界资源持有转移到 Flutter UI。
- `apps/app`：composition、导航和产品页面；不得定义资源算法。
## 4. Reader 数据流

```text
Reader interaction / viewport / presentation size
  -> ReaderObs
  -> RoleResolver + HeuristicPolicy
  -> DemandPlan diff
  -> PipelineReaderSession / LiveCoordinator
  -> DownloadSession -> DecodeSession -> UploadSession
  -> PipelinePageStream
  -> reader_runtime / Reader presentation
```

Reader 可以提交 stable page、fractional position、目标页覆盖率、阅读方向、viewport/physical target、interaction/zoom，以及 pause/resume/speed/jump 等命令。横向 paged 与纵向 continuous 的 fractional observation 在 current/stable、target page、target transition visibility bucket、visible page membership、playback phase 和 interaction control phase 均未变化时，PipelineReaderSession 在 enqueue 边界丢弃 control no-op，不重复运行 ReaderBinding、策略窗口或 output/artifact projection；播放 phase 与 transition threshold 的离散边界仍立即提交。

Reader 只能消费不可变页面状态、进度、错误和 `PipelinePageSurface`。它不得接触 mutable session、transport、artifact store、scheduler、cursor/frame handle 或 texture registry。`PipelinePageSurface.presentationIdentity` 是底层 presentation target 的稳定身份，而不是动画帧身份：同一 Android `SurfaceProducer` lease 的 WebP 帧只更新平台 texture 内容，Reader/UI 不得因此重建页面子树；lease、fallback image、尺寸或错误变化仍必须替换 surface 并更新视觉状态。动画帧通知（包括已有输出的瞬时 `uploading` 与 present 完成回调）不得重新执行 PlaybackGate 或额外触发 UI rebuild；同一 presentation target 的旧 claim 在平台 copy 完成后立即释放，真正改变 surface/lease/fallback 的 visual claim 才通过 `PipelineFrameScheduler` 合并到每个 frame 的单一 release drain。已有 surface 的 successor 若在 Flutter persistent callbacks 或下一帧已排队时到达，只合并最新帧并在该 frame 后提交，首帧仍立即确认，PageView/Reader UI 的 frame 预算优先于高频动画投影。横向 gallery 的 current/next/transition role 计划可由 Pipeline 在 host 挂载前建立有界 detached output；该 projection 不等待 upload ready、WebP sniff 或 decode classification，upload ready 后只预呈现首帧，未知 hint 的相邻页也不会错过预热；paged（LTR/RTL）animated/unresolved 的真实活动手势目标在既有 DecodeDemand 内额外拥有且仅拥有一个 priority-820 first-frame UploadDemand：稳定方向下的 `next` 仍按原路径工作；若 dragging/scrolling/settling 的 `targetCoverage.pageIndex` 已明确指向相邻 `previous`，即使 3/7 稳定方向尚未翻转，该实际目标也可暂时取得同一 frame-0 demand。LiveCoordinator MUST在该role进入prepare前冻结其playback，detached output MAY预呈现frame0到已预建的exact-size SurfaceProducer，但 MUST NOT推进隐藏successor/播放计时；当其后成为transition/current时恢复同一UploadSession/output，不得重传首帧。该 active-target 边界不得改变 3/7 方向状态、扩大decode/download窗口或扩展到next2；idle `previous` 不得因此获得 UploadDemand，vertical Reader仍禁止hidden animated preupload。该next projection在plan sync与host attach间继续绑定同一DecodeId，禁止临时unbind/prune后重复创建；manifest、已知 physical content kind 和明显非-WebP URI 后缀已确认的页面不建立无用 native output；current 且无 listener 或尚无 resident surface 时仍立即预热，next/transition 在 Flutter frame 已提交或排队时延后到 scheduler idle task，动画/触摸回调未清空前不得启动 platform create，仍继续解码且不改变 playback/freeze 语义，host attach 后立即同步最新帧，vertical Reader 不启用该 detached prewarm。Android texture lease prewarm 必须按 source canvas 等比 fit 后的实际 decoded raster 尺寸建立；DownloadSession 在 WebP 固定前缀解析出 source canvas 后立即触发 current/next/transition 的精确预热；同一 raster 尺寸的 deferred requests 按 current > transition > next 优先级每个 idle task 最多启动一个 platform create，idle+pending 总量仍受全局有界池限制；decoded frame 到达后的尺寸只作兜底，预热失败可重试且不得改变 demand/playback 语义。手势缩放是纯 presentation 行为：`ReaderView` 拥有 paged 单页 `InteractiveViewer`（双击分级默认 1.5/2.0 + 长按放大）与 continuous 整条 strip 的统一 `Transform`（双击分级 + 捏合 + 长按放大，所有页面一起缩放）。长按放大支持松手复原/保持释放（仅分页；连续模式始终保持）、拖动/聚焦两种移动方式、可调拖动比率、双击位置模式（居中/吸附/聚焦）与"最大可视"边界约束——该约束按 contain 后的真实图片矩形计算而非页面控件矩形，留边轴保持图片居中（契约见 SPEC 2.3）；这些是 UI 设置，不改变 demand/prefetch/texture 所有权或 NetLane 调度。strip 缩放是视口空间视觉层：滚动在放大状态下保持可用且跳页不复位缩放，未锁定时普通单指水平滑动可平移整条 strip；双击第二下按住仅固定当前倍率与水平偏移，按住期间独占指针并禁用垂直翻页，锁定时水平滑动不改偏移，双指捏合松开保持结果不弹回，已放大时长按仅水平拖动不改倍率；锁定态再次普通双击仅退出锁定，解锁后的普通双击才继续阶段循环；双击配对用屏幕坐标、阶段用离散索引单调推进（不受动画中间值影响），换级偏移按当前倍率换算锚点保持、动画向目标帧逐帧钳制插值不回跳不越界，放大态冻结延迟比例提交防止放大镜下内容改尺寸、回 1x 即落盘，仅方向切换/controller 替换等结构性变更复位；settled scale 经既有 `onZoomScaleChanged` 投影给 zoom decode boost，仅为可视区域提高解码分辨率。

## 5. 页面角色、窗口与优先级

`RoleResolver` 使用以下角色：

- `current`：stable page；
- `last`：仅用于 upload/output retention 的叠加标记，不占用相对页窗口；刚离开 current 的相邻页仍按 `previous/next` 参与 download/decode；
- `transition`：拖动目标页；横向覆盖率达到 0.15，纵向只要真实进入视口即建立；
- `next`、`next2`、`previous`：深度预解码角色；
- `near`、`far`：只保留 encoded download 的邻页；
- `detached`：窗口外。

稳定 encoded window 为前 7、后 3。深度 decode 角色窗口为前 2、后 1；更远页面仍可下载，但不获得动画深水位。

network 的 `NetLane` 与 decode/upload lane 都由 composition-owned scheduler 负责；current 的前台执行身份必须贯穿三条 lane：

- normal concurrency 仍为 network 5、decode 3、upload 2；network local bucket 2、remote source bucket 5；local/remote bucket limit 始终来自 `ReaderPipelineProfile`，不得以首帧/output readiness 临时改写；
- current priority 1000；network/decode/upload 各保留 1 个仅 current 可用的高优先级 handoff slot，transition priority 900 不占该保留槽；
- network `NetLane`以normal=5、current-only reserved=1为单一物理调度边界：normal priority 780/800/820/900只参与排队与active rank迁移，不得为了normal-slot pressure主动取消receiving task；current=1000在5个normal槽已满时先直接借第6个reserved槽，不得把“借handoff”本身实现为先cancel victim。只有normal+reserved均真实饱和且current持续blocked时，才允许统一`NetPolicyRank`按40分margin选择victim；破坏性preemption还必须满足NetLane-owned incoming candidate stability，Reader当前为100ms，free/reserved admission不受该等待影响。每个NetLane同一时刻最多一个preemption victim处于已cancel但未物理退出状态，其他blocked current继续排队/更新rank，victim真实退出后再pump，禁止一个scrub burst并行扩大取消面。logical claim归零的already-admitted task仍迁移rank0并标记`demanded=false`，queued未admit可直接移除；normal transport lease不足时优先回收这种inactive parked task；仍`demanded=true`的parked窗口成员只有在新的incoming按同一`NetPolicyRank`+40分margin明确胜出时才可被`ranked-transport-lease-reclaim`，从而避免低rank parked response把next/next2永久锁在队列里。consumer-bound transport真实dispose/错误/显式用户终止仍是独立硬取消边界。Venera单JavaScript request-plan permit继续独立使用controlled floor=780与current动态preemption，因为它保护的是单context invocation而非最终图片HTTP槽；gate同时观察waiter promotion与active current-class demotion，旧current降级且已有新current等待时重新执行同一40分preemption判定，普通非current demotion不触发取消；旧JavaScript必须真实`finished(requestId)`后才能转交permit。
- DownloadJob 不读取 holder depth、播放状态或页面控件；远端下载窗口、decode/upload execution reservation 与播放水位分别由唯一 owner 管理。

## 6. Decode 水位与 Transition 首帧

动态页面的 role 最大 holder 深度为：

```text
current / logical next / next2 / previous = 7 / 5 / 3 / 2
```

current 的浅水位 bootstrap 优先于 speculative neighbor：动态 current depth < 3 时，next/next2/previous 的实际 refill 目标暂为 0；静态 current 只需 1 帧。


```text
n>1, m>1, p>1, c>4, n>2, c>6, n>3, m>2, n>4（current bootstrap 已覆盖 c>2）
```

- local/content/file/asset prefix quantum：1 MiB；
- remote prefix quantum：256 KiB。

## 8. Animated WebP 生产与播放
```text
transport / artifact stream
  -> DownloadSession ingress
  -> native growing source
  -> demux metadata / NativeCursor
  -> process-lifetime Dart decode isolate
  -> libwebp single-thread frame decode
  -> premultiplied target-canvas RGBA
  -> FrameHolder
  -> UploadSession
  -> Flutter ui.Image/RawImage（Reader默认）或显式opt-in Android texture
```

稳定约束：
- durable READY 的 physical completeness 与 Reader-local encoded ingress hydration 是两个独立 ownership boundary：`DownloadSession.bindResidentImmutableAuthority` 可在正文已完整、promoted 且由 artifact-cache authority 持有时让 Reader projection 仍从空前缀开始；只有 DecodeDemand/UploadDemand/retained output 已经拥有 media source 时，`DownloadIngressProjectionRegistry` 才先回放 256KiB contiguous prefix，再按 DecodeSession 的 `requiredSourceLength`/native need-more-data 以 physical replay quantum 逐段增长。logical remote URI 不得把已落地 Direct/SAF body 重新按 remote cost 计价。READY backend 若能提供 generation-bound range reader，则 exact-length proof 与后续 range replay 复用同一 descriptor；reset/rebind/dispose 关闭该 capability。`ArtifactCacheReadScheduler` 只从真实 queued/active foreground local-read work（或明确的 operation-level holder）得到 foreground pressure；Reader presentation/current-output lifecycle不得预先制造 pressure，也不得保留“first foreground quantum”全局 reservation。该 pressure只影响本地读/写资源协调，不重新定义 page role、Download/Decode/Upload 水位。
- durable READY 的非WebP静态 presentation 可在上述body authority之外投影 generation-bound `ArtifactCachePresentationFileLease`：persistent store仍负责选择exact/verified physical replica，Android adapter只在lease lifetime内把Direct/SAF locator钉成只读PFD并暴露进程内`/proc/self/fd`；`ArtifactCacheManager`在交付前后校验mutation generation，Pipeline拒绝WebP/GIF并要求可信source dimensions，Presentation只消费file lease而不取得cache path/descriptor ownership。fd path不是缓存identity，Flutter ImageCache key绑定manager epoch + `storageId` + generation；平台/尺寸资格失败必须释放lease并退回既有full-byte path。该能力只删除eligible READY fallback的Dart整页encoded materialization，不改变3/7、decode2/1、Upload、NetLane、SAF executor或watchdog。
- Presentation 对 Pipeline WebP 首帧的接受必须原子同步 content format 与 ready state：一旦真实 Pipeline surface 已 present，`LocalImagePlayer` 不得保留旧 manifest/filename 推测（例如 jpeg）继续走 loading/fallback build 分支；首帧观测只在当前 surface 仍为权威时发布。
- opaque plugin URI不能让transport-cost policy等待完整animation metadata：physical/Reader ingress实际sniff到`ContentKind.webp`后，只投影runtime WebP cost evidence以启用既有bounded 5/3/2/1 body flow；该evidence不等于`animated=true`，DecodeSession的authoritative static/animated classification始终优先并可撤销cost-only推断；
- 两个 decode isolate 在进程期常驻；libwebp 帧内单线程；
- 首次 native 请求优先单帧，current 后续请求最多批量返回两帧；
- holder 是 decoded frame 的权威缓冲；可见 output 不计作 successor；
- 缺少 successor 时保持当前 output，等待 producer 通知，不进入 startup-buffer，也不阻塞其他页面 decode；
- playback 使用最近 deadline 的 one-shot wake；静态零时长帧不启动 timer；
- finite animation 到 EOF 保留最后一帧；
- metadata 未完成且 source 增长时允许刷新 demux；未封缄 `needMoreData` 等待 source revision，不用定时销毁 cursor；source revision 是 Reader-local projection 的状态事实，只有实际 decode fill 或 DecodeSession 已证明无需 fill 后才能记为 consumed，current-bootstrap 暂时门控邻页不得吞掉其 pending source wake； `SourceEpoch`的decode authority只属于Reader-local ingress projection，不得再由DecodeSession同时读取physical DownloadSession epoch形成第二generation owner；projection在同epoch内rebuild并替换`EncodedSource`实例时，DecodeSession必须释放旧cursor/holder并重新绑定当前source，异步decode期间projection epoch变化属于生命周期cancel而非内容failure，cursor复用必须同时满足projection epoch与source实例identity一致；
- target canvas 使用 contain 和 `height / width`，不裁切、不使用负位移或页面重叠掩盖接缝。

## 9. Upload 与 renderer output

primary可见upload角色仍为current、transition；paged Reader另外允许一个冻结的next first-frame preupload（不运行隐藏动画、不扩next2/previous）；上一 current 的 output retention通过独立 `retainedIndex`叠加 `last` upload demand，不改变该页的相对 previous/next 网络与解码角色。远离7/3窗口时 retention只保 output，不产生 download/decode。生产Reader保留native source/cursor/libwebp decode，但默认将RGBA一次转换为Flutter `ui.Image`并由`RawImage`呈现；推测静态邻页仍只可在既有预算内预上传。

生产Reader默认恢复Android SurfaceProducer output；dev.311 Flutter `ui.Image/RawImage`默认实验已被09:28设备证据否证并在dev.312回滚。SurfaceProducer路径仍使用默认platform MethodChannel、一个串行 blit lane和普通`mainHandler.post`；同一 output 的待调度回调可合并为一次主线程 `scheduleFrame()`，但每个调用仍必须收到完成回调，且 schedule 看到的是最新 resident frame。Reader WebP texture viewport 固定使用 `FilterQuality.low`，避免高分辨率页面首次进入横向 PageView 时同步生成 mipmap 抢占切页帧：

1. retain native frame；
2. 单 lane 复制预乘 RGBA；
3. platform thread 调用 `SurfaceProducer.scheduleFrame()`；
4. 原子替换 output retained frame；
5. 返回 MethodChannel；
6. UploadSession 记录 presentation 并推进 deadline。

生产SurfaceProducer路径的texture lease在output结束时真实释放，不回到Reader间复用池。只有从未呈现过的预热lease可短期复用，App非resumed时清理idle prewarm；deferred prewarm若与同尺寸的权威upload acquire竞速，池观察该进行中的acquire并等待其结果，不再创建重复SurfaceProducer。platform queue、schedule queue/call、blit和channel dispatch继续分别计时。正常逐帧 platform telemetry 不再在 Flutter isolate 生成重复 `frameUploaded` Trace，达到 20ms 或 deadline/surface transition 的异常样本仍保留，完整 timing 仍由 output/frame-pipeline 记录。

## 10. Reader 资源会话 retention

Reader Host 从 `PipelineReaderSessionFactory.acquire` 获取资源会话并在退出时 `release`。退出 Reader 不等于立即驱逐整章资源：

- retention pool 最多保留 2 个 media-empty idle 章节会话（LRU）；TTL 为 2 分钟；第三个不同key进入时立即完整淘汰最旧会话； 显式切换下载目录等 exclusive storage 操作必须先排空该 idle retention pool，再检查 composition transfer consumers；仍挂载的 active Reader lease 不属于 idle drain，必须继续阻止目录切换。
- key 包含稳定章节/source revision、loader URI/revision 和 composition 能力指纹；临时 loader 对象 identity 不参与；
- 保留Reader-local SourcePool、Decode/Upload/media runtime这些轻量容器以及对composition transfer runtime的consumer lease，但进入idle retention前其Decode/Upload session、Ingress projection、NativeSource与used output必须全部为空；physical DownloadRegistry、artifact/partial handoff与transfer workspace独立于Reader会话生命周期；
- 释放 Reader binding、page projection、playback wake、present claim 和 renderer output资源；
- 不同 key、TTL 到期、容量淘汰或 composition shutdown 时才完整逆序 dispose。

这是一条资源 lease，不是 Reader UI 缓存；SurfaceProducer不得跨Reader复用used output。

来源页打开已经持久化为 `LibraryComic` 的同一漫画时，source route lock 是该导航的唯一 presentation lock；不得在持有同一 `sourceId + raw comicId` lock 时再次调用会重复申请该 lock 的入口。路由锁只存在于内存导航生命周期，不写入 library，也不参与持久 identity。 `LocalComicDetailsScreen`不得持有external source availability的永久nullable快照：route进入可先等待deferred source publish，但未持久化章节的loader每次执行都必须通过Home的live resolver重取source；因此同route重试可在source稍后就绪后恢复。

## 10.1 Reader progress 与阅读历史

Reader 页面变化产生的 `ReadingProgress` 由 `reader_runtime` 串行合并后写入 App 提供的 progress facade。同一 Reader 同时只有一个 active writer；较新的 pending progress覆盖尚未开始写入的旧值，禁止并行 Future 倒序完成后覆盖新页码。

普通页面变化只 enqueue checkpoint，不等待 SQLite；但正常 Reader route 返回前必须先 drain Reader-local pending writer，再通过 `ReaderProgressCheckpointStore.flushProgressCheckpoints()` 等待 storage-owned SQLite writer 的 durable barrier，完成后才用 route-local `latestProgress` 替换 Home/详情内存投影一次。`inactive`、`paused`、`detached` 也执行同一 checkpoint+flush，但不得把 durable barrier扩散到普通翻页。操作系统在 barrier 前强杀仍可能丢最后窗口，文档和 UI不得声称绝对 crash-safe commit。

## 11. Identity、缓存与 artifact
不同 identity 层不可混用：catalog identity 定位实体；DownloadId 表示确定字节版本；DecodeId 还包含 epoch、target 和 renderer；presentation identity 只表示页面位置/输出。

缓存分为两个权威平面：

- `ResourceCacheCoordinator.responses`：封面、搜索、详情和章节元数据，使用稳定 namespace/identity/revision、weight、TTL 和 in-flight join；external artwork 使用 source-confirmed canonical comic identity + role，raw runtime locator 不参与 durable artwork 分区；
- `ArtifactCacheManager`：Reader 不可变页面 artifact，默认热字节 10 项/256 MiB、alias 上限 8192，并连接持久 backend。底层 `SqliteIndex` 与 `PersistentDownloadArtifactStore` 维护内存快照并对 `readyPageIndices` 与 `indexedRecords` 提供 O(1) 探查；正常 sealed Reader 热读只做存在性/长度等 O(1) 元数据校验并直接流式消费，完整 CRC-32 属于 seal/materialize/显式 repair-audit 边界，不得在每次读取时全量重算。SQLite schema 8 已把 immutable object proof 与 physical copy 分开：`artifact_object` 保留 bytes/checksum 与兼容 locator mirror，`artifact_replica` 才是 sealed 物理副本权威；同 artifact 可有多个已验证 replica，Direct/SAF 同根 proof 只增加该 replica 的 access alias。partial 不属于 replica。多个ready logical bindings共享同一`artifact_id`时，cache capacity/trim按该physical artifact只计一次正文；任一sibling受到pin/busy/protected约束即保护整个physical group，只有最后logical binding移除并真实删除replica时才计入released bytes。结构性坏副本只淘汰自身，不得连坐 logical binding 或其他 sealed replica；`accessDenied/ioFailure` 只影响访问可用性。 `lengthChanged`的破坏性置信度按access kind区分：Direct/POSIX一次exact mismatch即可structural；SAF必须独立重开/重取长度二次确认，bound READY reader若首次descriptor长度异常也关闭并重开一次，只有重复mismatch才退休replica，第二个descriptor恢复sealed length时直接成为后续range authority。

封面 URL/token 不是稳定 comic identity；verified checksum、来源 page key、内容 hash 或用户确认迁移才可登记 artifact equivalence。App/Reader 不得创建私有图片字节 LRU，也不得让 cache hit 共享 cursor、timer 或 decode identity。 Durable READY 的 crash-recovery ownership 与 canonical physical routing 统一收口到 schema-8 SQLite authority：`artifact_object` 持 immutable bytes/checksum proof，`artifact_replica` 持 sealed physical locator，`cache_entry` / `physical_media_artifact` 分别只是 logical/exact binding 与 canonical routing；`cache_entry.path` 和 final `.meta` 都不得反向成为 sealed body owner。dirty `StartupRecovery/CacheScanner` 只清理没有 DB/live authority 的本地 crash garbage，并保护 DB-authoritative replica locator；它不得因 `.meta` 缺失、格式损坏、ownerless、checksum/path 字段不同而创建、删除或重建 READY，也不得为 READY 重新 materialize `DownloadSession`。真实正文缺失、exact-length mismatch、unsafe locator 等结构失败仍由普通 artifact→replica read path typed 检测并只退休坏 replica；多 replica 时不得连坐其他副本或 logical/canonical binding。mutable partial/spool继续是独立 authority，sidecar只可补充 validators/resume/collision diagnostics，不得把 partial/final bytes 升级成 durable READY。`PersistentDownloadArtifactStore.storePromotedArtifact()`遇到 matching READY 时先走 artifact/replica preflight并直接复用，不得调用 session restore 去“修”sidecar；只有真正的新 materialization 才进入 mutable `DownloadSession`。final data rename 与 SQLite artifact/replica commit 之间的崩溃窗口由 schema-17 `artifact_promotion` progress journal 闭合：journal 只从已索引sealed length/CRC proof建立并同时保护source/destination候选，open按DB proof完成rename/commit或fail-closed回到partial；它自身绝不成为READY，也不读取sidecar。automatic `PromotedArtifactCacheHandoff`继续复用 matching canonical sealed body，explicit exact persistence仍通过metadata binding/materialization满足用户durability语义。

orphan，不执行 READY registry restore；mutable partial 的 demand-time adoption/resume仍由其独立 physical/index owner负责。非权威exact locator的crash清理由download-cache schema16 source失去authority前登记；`obsoletePartialSource`只冻结跨locator replacement或cold retirement瞬间的旧mutable prefix generation，切换前按实际旧body计算length+CRC32，普通append/pause/checkpoint不得付该CRC成本也不得把此proof当partial validity。普通`PhysicalPartialRecord`删除失败时必须保留row直到body+sidecar确实清除，不需要另建debt。跨进程obsolete cleanup都必须先确认locator已非replica/partial/migration authority并重新校验当前bytes仍匹配旧proof，路径被复用/内容改变时只能撤销cleanup intent、不得删除；hot session接管旧path时也必须撤销provisional partial cleanup。store open只异步枚举这些小型debt rows并经`StorageWriteScheduler`定向处理，SAF只处理当前同tree、绝不tree scan；跨locator physical partial copy不得以较短失败staging覆盖较长旧prefix，legacy exact Direct→SAF在旧root不可安全检查时必须fail closed。schema9 `artifact_replica_migration.copying`仍是可resume进度，在schema9 owner存活时不得被generic cleaner触碰；同一proven 权重，response 目标保持固定小默认值；`ResourceCacheCoordinator.updateMaintenancePolicy` 只更新策略，回收发生在下次 `trim()`（设置页应用后立即触发一次并刷新用量），retained artwork 不受容量整理影响的规则不变。人类可读的结构化导出目录以 exact `(sourceId, comicId)` 对应的持久化 `DownloadPlacement` 为权威。物理目录不存在（`!dirExists`）或无真实图片（`!hasRealImages`）且无活跃会话认领时，无条件判定为空闲并释放历史游标，优先分配纯标题目录；物理存在的非空目录冲突时弹出用户选择，严禁静默重命名或让历史 SQLite 幽灵记录阻断纯标题目录。任务意图（`DownloadPlacementMode.incremental` / `overwrite` / `createNew`）与落盘目录及 `pageOrder`（`ComicPageOrder.auto/chronological/origin`）持久化于 SQLite `download_placement` 表中，单章和整本任务都重放同一 placement；仅对升级前缺少 placement 且全部已校验记录唯一指向同一目录的任务，允许从 `CacheRec.path` 一次性迁移。`pageOrder=auto` 只是一项未解析的导出布局意图：第一次真实结构化导出前，仅当当前漫画确认为单章且已有 verified `ComicVersionPageMapping` 证明 pure front-prepend 时冻结为 `chronological`，否则冻结为 `origin`；来源字符串、Venera/E-Hentai 身份或当前总页数均不得作为反序证据。SQLite schema 6 的稀疏 `export_page_binding` 只为实际进入导出的 `(source, comic, chapter, page)` 保存 immutable `exportOrdinal` 与可更新 logical index；同 comic 前置追加以及跨 comic 的 verified version chain 都通过既有 binding/compact relation 惰性继承旧 ordinal，新页只在已用最大 ordinal 后分配，未打开/未导出的中间版本不创建逐页行，因此不得再用全局 `N-index` 重算或推后旧文件名。普通 Reader 永远按来源 logical manifest 顺序读取，`DownloadPlacement.pageOrder` 不参与 Reader 排序；只有用户启用 per-comic 设置后的 `invertPageOrder` 是 presentation override。物理页序改变不是 Reader 行为，现阶段也不存在普通 `flipComicPageOrder` fast path；未来如需要只能作为显式 Export Relayout migration，在 SQLite generation 与物理 rename/move/materialize 一致提交。普通下载/重试不枚举目录或收编未索引文件，只消费下载过程中逐页持久化的非空 CRC32 校验记录；未索引文件在目标提交时形成显式冲突，独立 repair/audit 才可扫描。最终目标路径提交由唯一 `PersistentDownloadArtifactStore` 串行化：经用户授权的 overwrite 模式允许覆盖更新 `.zic.json`；同进程已有旧 owner 认领时也必须由 `observedOwnerKey` 精确匹配该 owner 才可替换，未授权冲突抛出显式 `ErrorCode.policy` 错误。跨版本 createNew 复用必须物化到本版本的 1-based 目标页路径，并在复制前后验证 bytes+CRC32。结构化页 materialization 的最终图片扩展名 MUST 由 bounded byte-signature sniff 决定而不是来源 hint/文件名；当前支持 JPEG/PNG/WebP/GIF/BMP/TIFF/ICO/AVIF/HEIF，ISO-BMFF 必须命中明确 AVIF/HEIF brand，generic `ftyp` 不得猜作 AVIF。已进入结构化图片导出的正文若无任一支持签名 MUST 作为 `artifactCorruption` 拒绝，`ContentKindHint` 不得覆盖实际非图片 bytes。每个目录的 `.zic.json` 描述当前 owner、稳定章节目录映射、单调 generation 与内容 fingerprint，placement 镜像最近提交 token；POSIX 通过目录锁串行提交，SAF 校验 record tree URI 并用临时文件加 replace/recover 协议提交，但 manifest 字节、placement 与 SQLite binding 尚未形成跨进程单一事务。整本队列把执行期 `ErrorCode.policy` 提升为持久化 `requiresUserAction` 阶段，保存冲突目录、existing/request owner 和触发章节，停止后续调度；详情页再次发起整本下载时必须重新弹出冲突对比并以新 placement 重建任务，管理页不得把该阶段当普通失败直接重试。长期数据模型仍需进一步把物理 artifact、逻辑版本 binding 与 export binding 彻底解耦。

### 11.1 当前生产代码的 key/id 对照
整本下载重新形成 placement 时，目录、模式与 observed owner 作为一组整体替换旧任务授权；`createNew` 因此可以明确清空旧 owner，避免重试再次携带旧版本的覆盖许可。

以下是现有实现中容易被混称为“key”的几组身份。它们的用途不同，不能用标题、显示名或图片 URL 互相替代。

| --- | --- | --- |

| raw `comicId` | 来源原生 runtime locator | `Comic`、`SavedComicRecord`、`LibraryComic` 与章节归属保留的原始漫画定位值。Mihon 可把可变 SManga 快照编码进该值，因此它只保证“如何再次调用插件”，不得假定为 durable artwork identity。 |

### 11.2 同源版本与迁移身份

同源版本必须区分以下身份，任何一层都不得用标题或 URL 字符串替代：

- **raw locator identity**：`sourceId + raw comicId`，是插件请求、SavedComic、章节归属和迁移前后实体的真实定位身份；同一来源的新旧版本必须保留不同 raw comicId。
- **canonical comparison identity**：来源确认的同源等价比较值，只用于归并重复投影和比较候选；它不能替换 raw locator，也不能直接改写章节、页面或下载 key。
- **version relation identity**：`sourceId + predecessorComicId + successorComicId`。关系必须由 `ComicVersionSource` 或已持久化的来源确认结果产生；标题搜索结果不能自动成为版本关系。
- **chapter/page identity**：章节始终为 `sourceId + chapterId`，Reader 页面为 `sourceId + comicId + chapterId + pageId`。迁移时只有章节原生 identity 精确匹配才复制阅读进度和已读状态；**sequence-only** 匹配仅显示在比较报告中，不复制状态。
- **presentation identity**：Flutter key、详情提示和 Reader 一次性提醒只能引用上述稳定复合身份；Widget key、当前章节、封面 URL、按钮状态和 runtime adapter 对象都不是持久身份。

同源 successor 发现后写入 `ComicVersionRelationStore`；`HomeLibrarySession` 在 enrichment 时一次加载全部 relation，并在新 relation 写入时同步更新内存投影，因此 Home/source browser 无需依赖详情页副作用即可判断旧版更新。source-card `!`按relation predecessor/successor的raw+canonical identity区分，不能因library alias归并吞掉predecessor或在successor误报。详情页multiple versions先选择；详情/version-state与Reader都可异步检查版本。显式查看版本时，目标详情route持有`originComicId + reuse-preparation Future`直到该target route退出，不能因前置Future先完成就丢失selected-version上下文；目标Reader hydrate当前chapter后、创建physical demand前先等待前置Future，再只针对`origin ↔ target` direct relation做一次target-side bounded catch-up。generic Reader不等待这条barrier，也不扫描历史。proof形成后`HomeLibrarySession`把exact version page的verified interval编译为compact canonical projection；落入projection的`DownloadId`在session创建前直接解析为版本无关`PhysicalMediaId`，目标版本新增/未验证区间保持exact-only。Reader启动后继续异步metadata/version refresh；既有pre-canonical physical generation可由兼容alias自然退休，但新hot-path不再通过版本carrier ranking定义physical identity。cross-version cold durable state仍只在physical prepare的durable tier参与恢复，provider request/validator继续由每个claim的exact `DownloadId`拥有。确认迁移后只复制library实体状态；媒体artifact不做hard alias/rekey。同漫画多版本的 durable relation store 是历史证据层，不是运行时选择器。`HomeLibrarySession` 在 relation/shelf preference/manual snapshot 变化时重算 `latestKnownHead / shelfHead / downloadHead`，并把唯一可证明的历史路径折叠成 direct predecessor→downloadHead mapping 后只注入 manual/export 子路径；artifact cache 同时独立接收完整 source-verified relation 集，绝不因 downloadHead/是否显式下载而丢失 cache reuse。DownloadManager、ExportLayout 和章节下载执行不得自行 BFS/求传递闭包。不同版本 chapterId 只有折叠后的 `pageMappings` 明确对应时才归并；direct baseline relation 缺 mapping 的 legacy 情况才允许 same raw chapterId 兼容。当前 Presentation 不建立旧版子项树；被 downloadHead 取代的旧手动 row 只从主列表投影隐藏，其 exact durable placement/artifact 与删除 authority 仍保留。source 新版只成为 `latestKnownHead`，必须经过书架迁移或显式下载后才分别成为 shelf/download head。

## 12. 插件与网络边界
网络默认 User-Agent 属于 composition-owned 请求策略。AppPreferences 保存当前 fallback UA，默认使用稳定 Android Chrome UA；`main`/composition 以动态 provider 注入通用 `HttpTransport`、Reader/章节下载 fallback、插件仓库 control-plane 与 shared source host transport。来源 request plan 显式 `User-Agent`、Mihon browser-session UA或 source-owned client策略拥有更高优先级，全球设置不得覆盖这些来源权威。Presentation 不得自行构造 HTTP client。

网络执行只有三类合法 owner：
- **source-owned client**：Mihon/Venera 等来源的 CookieJar/interceptor/auth/DNS/TLS/session 语义；未知 client wrapper、重定向、`Set-Cookie` 或无法无状态平铺的响应必须留在这里执行；Venera JavaScript `Network.*` 的 Cookie、manual redirect、`cache-time`、`prevent-parallel`、requestId grouping 与同步 JS contract 仍由 plugin-host source runtime拥有；其中 Venera source-requested resolver cache 属于runtime-network composition，`NativeExternalPluginDriverHost`持有唯一有界`VeneraHttpCacheStore`并以`pluginId/pluginVersion/sourceKey`分区，单个WebView/`VeneraNativeBridge`只消费而不得拥有或在close时清空，同namespace bridge replacement可继续复用仍新鲜的resolver entry。 显式用户resource fresh generation是这个复用边界的例外：`fresh:true`重新执行source hook时，只给该hook实际发出的`Network.*`调用附加request-scoped fresh语义，由同一cache owner逐URL force-miss并以新origin response重新填充；不做source namespace级清空，也不把fresh resolver行为变成新的retry owner。HTTP execution 不再由 Kotlin `HttpURLConnection`/DoH/reflective OkHttp拥有；isolated plugin Dart process 持有 reusable rhttp/reqwest resolver client 与 requestId→CancelToken 映射。resolver rhttp 的 transport failure 必须以typed retryability跨 Dart MethodChannel→Kotlin bridge→WebView JS runtime 保留，不能退化成字符串后靠错误文案正则重新猜测；`venera-resolver-http-failed` 属于network failure并继续交给既有physical `DownloadTransferOwner`/provider `RetryPolicy`，bridge/runtime自身不得因此新增第二retry loop。最终 media replay继续由主流程的 rhttp direct transport执行。由于两者位于不同进程，不能共享同一物理client/连接池，但必须统一到同一 rhttp client family；Kotlin/WebView不得重新建立第二HTTP connection pool。
- **统一 host transport**：仅重放来源已经解析成无状态 request plan 的单次资源请求。生产 Flutter composition由 `downloads_bridge` 注入可取消的 Rust/rhttp streaming transport并复用client/keep-alive；rangeStart=0 的完整/首段response通过媒体前缀校验后保持raw streaming cadence，合法206且`Content-Range.start > 0`的中段不得再次要求完整图片magic header，应直接保持raw stream/cancellation/diagnostics；不得仅因中段不含文件头而转runtime fallback，也不再建立第二套64/256KiB framing。transport packet边界由 `DownloadJob` 统一聚合为首批约16KiB、后续64KiB source-progress quantum后才进入session/native/artifact；pure `downloads` 的 Dart HttpClient只作为非Flutter/test默认。两者都关闭自动redirect，只有无 Cookie状态变化且直接返回编码媒体时才有资格把字节交给 Pipeline，且平台 transport必须观察同一个 `TaskControl`。rhttp持续传输观测只允许通过`ByteResponseReadDiagnostics`在stream结束/取消时snapshot receive-progress与raw-body cadence；HTTP version和匿名endpoint hash仅用于trace。该seam不得提供pause/resume、bandwidth quota或priority，也不得进入Reader/Pipeline/session policy； Venera source 的图片正文还有一层独立于transport retry的source semantic contract；该能力只属于host-private image binary seam，public `Network.fetchBinary/http_binary`继续允许任意binary：rangeStart=0的2xx正文若在image-private native/runtime边界已证明不具备受支持图片magic signature，必须在注册native-byte token/交给Dart之前判为image-load failure并失效该URL的runtime HTTP cache。host direct/rhttp把这一事实标成`sourceMediaSemanticRejected`；`SourceResourceTransport`由单一source-recovery owner在一次logical open内最多消费5个当前config的`retryResource/onLoadFailed` replacement，而不是因笼统`sourceMediaProtocolMismatch`把原locator送入full-runtime，也不得让provider RetryPolicy另起semantic retry层。`sourceClientStateRequired`才表示redirect/Cookie/interceptor/session state必须交给source-owned runtime client。Venera retained config以`semanticRetryCount`共享streaming与full-runtime剩余预算：replacement自己的`onLoadFailed`可继续生成下一config，达到5次或无callback才转non-retryable `ErrorCode.source`；同一retained logical resource不得fresh-resolve原`onImageLoad`逃逸该预算。
- **control-plane HTTP**：插件仓库索引/APK/JS安装等，不属于漫画 response cache，但仍使用 composition 的默认 UA fallback。
Venera 的 canonical source WebView 继续是唯一 stateful JavaScript invocation context，保持单 invocation；不能为了图片变换吞吐把整个 source runtime 并发调高。source request plan 若显式导出可隔离的纯 `modifyImage`，且脚本不依赖 `onResponse`、source/browser/network 可变状态，则可进入独立 image-only transform context；该 context 不加载 source script，只暴露 `Image` bitmap primitive，不拥有 `Network`、Cookie、settings 或 source data。静态资格不成立或运行时发现缺失 source global 时返回 incompatible 并重新经过 canonical source gate；`onResponse` 始终只在 canonical context 执行。image-only context 因此是 CPU transform execution plane，不是第二个 source owner，也不得在 transform gate 下偷偷调用 canonical WebView。Reader 首个 presentation frame 后的 metadata/version/reuse warmup 属于 application background source work，不再由 first-frame callback 直接发起无优先级 source invocation；生产实现把整条 refresh（comic/chapter metadata、version discovery、version-reuse warmup 以及其 verified-reuse resolver probe）作为 priority 100 任务提交到 application-level `DownloadResourceCoordinator.networkLane`，同一个 scheduler `TaskControl` 经过 `ControlledComicSource` / `ControlledComicVersionSource`、`CachedBrowsableComicSource`、plugin runtime adapter 与 `SourceResourceTransport.verifiedReuseIdentity` 一直传到底层。受控 warmup 不得 join 一个没有该 token 的 generic coalesced Future，否则会重新丢失 cancellation/priority owner；前台 page-plan 仍使用既有更高 rank，并可由同一 NetLane/runtime gate 让后台 metadata 退出，Venera 唯一 permit 仍必须等被取消 invocation 真实结束后才能转交。这里没有 Reader 私有 timer、metadata lane 或第二 scheduler。
`ResourceCacheManager` 是可重新获取 metadata/artwork response 的唯一缓存 owner。Catalog browse/details/preview/comment/chapter 只管理 metadata，`CachedBrowsableComicSource` 不提供 artwork loader facade；封面、预览不得直接取得 raw source transport。章节正文/Reader page body 明确由 DownloadSession/artifact/Pipeline 管理，因此通过 `ComicSourceResourceGateway.pageResponseLoaderFor/loadPageBytes` 绕过 response cache。两者必须复用同一 source-resolved response loader；full-byte fallback不得直接调用 `source.loadResource()`。章节下载侧只接受原子 `ChapterResourceAccess`，不得分别更新 byte loader 与 streaming transport。

插件先生成 request plan。GET/HEAD 必须零 body且不得携带实体 headers。Mihon 页面资源必须从 `HttpSource.imageRequest(page)`（或等价 source request）保留准确 URL、method、headers和必要的小型 request body；共享 transport不得注入 Venera专用默认 UA。Android宿主必须提供可执行 source实际返回 HTTP(S)媒体 URL 的统一网络能力，不能按具体插件/域名维护 cleartext白名单或擅自 HTTPS改写；URL选择仍属于 source/request plan。宿主直连前同步投影当前 source OkHttp CookieJar Cookie与同站点 browser-session UA。若宿主 HTTP成功但响应前缀不是支持的编码图片，字节不得进入 Pipeline/decoder；这属于source image semantic rejection，应由同一个source-recovery owner按当前config的`retryResource/onLoadFailed`有界推进replacement chain，而不是把同一原URL转入runtime重放或让provider retry重复消费semantic recovery。只有宿主无法保留source client state时才使用source-owned runtime network兼容路径；普通可重放图片仍由宿主流式 transport进入统一 Pipeline，完整图片正文不得仅因 Cookie/header需求改走 JSON/Base64 RPC。页面下载的 retry只有 `LiveCoordinator` 一个 owner：runtime transient错误必须投影为 `ErrorCode.network`后进入有界重试；非 retryable/source错误或重试耗尽在当前 demand内成为 terminal，source listener/finally不得自行重复提交。

Cloudflare 可见浏览器的 Cookie 与 User-Agent 必须属于同一个浏览器 session。验证模式下 `NetworkBrowserActivity` 不得把插件/OkHttp 的静态 UA 写入 WebView；WebView 使用当前 Android WebView provider 的真实 UA，并把该 UA 与同站点 Cookie/localStorage 写入同一 snapshot revision。Mihon runtime 读取 snapshot 时不再要求它等于启动前的静态 UA，而是在 OkHttp application interceptor 中对同站点请求逐请求采用 snapshot UA；CookieJar 同步导入同一 revision 的 Cookie。这样避免 `cf_clearance` 来自真实 WebView、HTTP 请求却继续声明另一浏览器/平台所产生的 Cloudflare 指纹不一致。

`sourceVerificationRequired` 只由 host-owned typed `SourceVerificationRequiredException` 产生。`cf-mitigated: challenge` 是明确协议证据；否则 HTTP 状态必须为 403/503、`Server` 必须是 Cloudflare，并且 HTML 必须含 Mihon 同样使用的 `challenge-error-title` 或 `challenge-error-text` 实际交互 challenge DOM。仅出现 `challenge-platform`、`cf-chl-*`、`Just a moment`、Cloudflare Server header或普通 403/503都不足以触发浏览器验证，避免把 geo/access block误分类为可通过 WebView解决的验证码。异常 envelope 同时携带实际失败 request URL、HTTP 状态和请求时 `cf_clearance` 是否存在；这些字段只用于恢复路由和诊断，不进入持久 identity。Mihon 主网络和 ABI兼容 interceptor均委托同一个 detector；不得创建隐藏 WebView、等待 challenge或按异常消息文本猜测。
插件和平台桥不得导航、创建 Reader、提交 demand、直接读写 artifact、访问 App controller，或把 Cookie/token/Base64 payload 原文写入 Trace。
## 13. Telemetry 与关闭
状态所有者产生权威事件；App 只做有界导出。Debug Trace 的文件落盘由单一 App export service 拥有：它统一 snapshot、JSONL 编码、文件名和目标目录，首页快捷入口与 Trace 页仅提供不同事件集合。目录策略由纯 App destination model 拥有并持久化为 `Download/` 下的相对子目录，默认 `Debug`；Android bridge 使用 MediaStore 写 `Download/<relative>/` 并只做最终路径安全复验，不能形成第二套目录策略。composition physical transfer事件对共享App/export sink只能写一次；每Reader可保留独立memory trace projection，但不得经多个Reader wrapper把同一physical event重复写入同一全局sink。跨 Home/Details/SourceBrowser/Reader/Pipeline 的 `TraceEvent.monotonicMicros` 必须来自同一 process-monotonic `SystemClock` epoch；route-local stopwatch只允许计算局部 duration，不能作为可跨组件排序的事件时钟。physical DownloadSession 的trace identity跟随physical owner token而不是偶然exact anchor；长 decode/upload/provider identity可由owner一次性生成与`TraceEvent`脱敏规则完全一致的稳定token并复用。长 identity 使用 hash/长度摘要；导出投影可按稳定语义桶合并高频诊断样本，例如 `framePipelineTiming` 按 trace reason / dominant stage / role，`decodeRefill` 按 role / stage / source-wake 分桶，并保留 first/last、count 与关键 timing/source revision 的 min/max。该合并只属于导出观测，不改变运行时事件或策略；错误、retry、writer rejection、resume/source read、session retain/reuse 和生命周期边缘不得因导出压缩丢失。overlapping total 不得与子阶段重复参与 dominant 归因。 production rhttp 的HTTP version与匿名endpoint hash属于每response低开销观测；高频native receive-progress只允许non-product或显式诊断构建启用，且不得改变transport cadence或成为调度输入。
完整关闭遵循依赖逆序：停止新 demand，关闭 upload/decode/download，释放 frame/output/texture，关闭 runtime scheduler与 workspace，最后由 App 关闭其创建的平台 facade。外部注入 capability 不由消费方关闭。
## 14. 静态门禁
静态门禁阻止明显的依赖反转、API 泄漏、重复权威和文档漂移，但不能替代 `flutter analyze`、Dart/Flutter/Rust tests、Android debug/release build 和真机生命周期/性能验证。
Detailed download/storage ownership for multi-version materialization, SAF/direct coexistence, partial transfer continuity and Reader/manual resource sharing is defined in [`DOWNLOAD_STORAGE_ARCHITECTURE.md`](DOWNLOAD_STORAGE_ARCHITECTURE.md), with normative rules in [`DOWNLOAD_STORAGE_SPEC.md`](DOWNLOAD_STORAGE_SPEC.md). The production decomposition is `VersionHistory/VersionBaselineResolver + ArtifactRepository + StorageRootRegistry + ExportLayout + TransferCoordinator + StorageCoordinator + AppResourceCoordinator`; Pipeline remains Reader-specific and consumes shared capabilities rather than owning application-wide network/storage policy. Durable chapter metadata is App-private `chapter_downloads.sqlite` with one-time validated legacy `cache.sqlite` import. Schema 7 owns persistent root/access identity and health; proven Direct/SAF locators for one system ExternalStorageProvider root are aliases whether the tree is `primary:` or a uniquely resolved current `StorageVolume.uuid`. UUID/path mapping is only candidate discovery and never root authority: the existing bidirectional canary remains mandatory, same-SAF reproof after a mount-path change keeps one `StorageRoot`, newest verified healthy Direct is preferred, and `accessDenied` degrades only that locator. Schema 8 owns sealed physical copies through `artifact_replica`: `artifact_object` is immutable proof plus compatibility mirror, ready v7 objects migrate to stable replica one, partials never become replicas, and additional copies require exact-length + CRC32 verification. Reads resolve artifact→replicas→proven aliases; structural failure retires only that replica, while access/I/O failure preserves it, and mid-stream fallback never splices independent copies. The final logical-binding removal cleans all registered replica bytes. Existing whole-root POSIX migration rewrites replica locator/root while preserving `replica_id`. Schema 9 persists progress-only `artifact_replica_migration` state for durable sealed-replica relocation; schema 10 is the migration-completion marker for the chapter-download metadata DB, so legacy artifact/root/download-identity backfills execute only while upgrading from v1-v9 and MUST NOT rerun on every current-schema open.  during `copying` the source replica remains authority and the deterministic temp is non-authoritative; after restart, Direct/current-SAF temp bytes resume only from a physically measured length after whole-prefix CRC32 comparison with the sealed source, while unprovable or mismatching prefixes restart from zero. Destination length+CRC32 is still fully verified before one SQLite transaction moves the same `replica_id`/compatibility mirrors and marks `cleanupPending`; failed source/temp cleanup survives restart as debt and never rolls authority back. StorageRoot alias merges, whole-root byte migration and final logical invalidation keep this progress state coherent. Automatic lazy convergence/retention policy remains a later boundary. Root-relative replica persistence is HOLD: current schema-8/9 absolute locators are compatibility mirrors, while destructive read/delete/migration cleanup now re-resolves the same relative locator through proven StorageRoot aliases after remount; no schema-17 authority is justified by current evidence.
