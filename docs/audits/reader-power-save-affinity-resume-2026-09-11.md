# Reader power-save affinity resume audit — 2026-09-11

The late Reader slowdown is a two-stage effect, not one monotonic media leak.

In the pre-fix device trace `zic-debug-trace-2026-09-11T10-11-38.jsonl`, the run is healthy immediately before a 46.004s event gap: native WebP decode samples are about 40–48ms. The last event before the gap is at 419.738s; the next Reader reuse is at 465.742s after 47.508s retained. Immediately after that gap, the same 1072×1608 decode path records native decode around 157–159ms and decode dispatch around 39–95ms, while an intervening frame can still decode around 42ms. This pattern is consistent with a process scheduling state change, not permanently harder media content.

The MIUI device reproduces the scheduler boundary mechanically when Battery Saver is enabled from the right-side control center. While ZIC is backgrounded behind Settings it is correctly placed in `/background` and limited to CPUs `0-3`. After 30s in the background and returning ZIC to the foreground, ActivityManager reports the UID as `TOP` and both cpu/cpuset cgroups are `/top-app`, but `/proc/self/status` remains `Cpus_allowed_list: 0-3` at 200ms, 1s, 5s and 15s after resume. In the same Battery Saver state, Settings as the foreground `/top-app` process has `Cpus_allowed_list: 0-7`, so the restriction is not a universal Battery Saver foreground policy. Disabling Battery Saver immediately restores ZIC to `0-7` without restarting the process.

This explains the local slowdown but not the former 268–295ms Flutter build stalls. Those were a second-stage amplification: replayed page dimensions and adaptive-profile evidence could rebuild the whole paged Reader. After localizing page-ratio updates and removing the redundant screen-wide adaptive `setState`, a seven-cycle A/B Venera + local-folder device run produced 1459 Reader frame samples with zero builds >=20ms, late p99 build 4.34ms and max 13.13ms, despite process memory pressure remaining non-trivial.

Production must not restore the old `sched_setaffinity` experiment or fight the OS power policy with hidden APIs. The durable response is: keep Reader updates local so degraded CPU capacity does not amplify into whole-screen rebuilds, and record lifecycle scheduling evidence so future traces distinguish media work from OEM scheduler state. The app-level trace now records Dart lifecycle plus Android `powerSaveMode`, process importance, cpu/cpuset groups, `Cpus_allowed_list`, and available processor count. This is observation-only and must not drive Pipeline scheduling policy.
